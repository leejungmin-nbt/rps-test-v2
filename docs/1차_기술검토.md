# 가위바위보 챌린지 — 1차 기술 검토

본 문서는 가위바위보 챌린지 이벤트를 **백엔드 신규 개발 없이** 프론트엔드만으로 구현 가능한지 검토하고, 가능한 경우 어떤 방식으로 구현할지를 결정한 1차 기술 검토 결과입니다.  
(실제로 적용해본 상황은 아니다보니 검토 내용이 변경될 수 있습니다.)

## 0. 요약

* **수행 가능.** Firebase + Cloud Functions 만으로 PRD 핵심 기능 구현 가능해보임
* 동접 기준은 **1만명**으로 산정
* 1회 행사 비용 약 **$1\~$2**, 월 4회 합계 약 **$5\~$10 (테스트를 통해 도출한 결과가 아님)**
* 수행 전제 조건:

    1. Firebase 프로젝트 사용 + Blaze 요금제 활성화
    2. 운영적 trade-off 수용 (정원 ±5% 초과, 운영자 수동 적립)

## 3. 동접 1만명 관리 방식

### 3.1 1만 기준에서의 인프라 부담

| 항목 | 1만 기준 부담 | 처리 방식 |
| --- | --- | --- |
| Firestore 단일 문서 broadcast  | 1천\~1만 listener 가 페이즈 변경 수신  | Firestore 가 자체적으로 처리 (수십만 listener 까지 가능)  |
| Firestore 쓰기 (입장)  | 1만 회  | 분산 샤드 카운터로 분산 처리  |
| Firestore 쓰기 (라운드 선택)  | 1만 × 라운드 수  | 참여자별 문서이므로 자연 분산, 부담 없음  |
| Firebase Hosting 트래픽  | 약 50GB  | Blaze 요금제로 자동 확장, 비용 \~$0.50  |
| Cloud Functions 호출  | 라운드 페이즈 전환 시마다 1회  | 무료 한도(월 2M) 내  |

### 3.2 정원 게이트 (분산 샤드 카운터)

```
counters/shards/0:  { count: 47 }
counters/shards/1:  { count: 51 }
   ...
counters/shards/9:  { count: 49 }
   ▲
   │ 클라이언트는 0~9 중 무작위 1개 샤드에만 +1
   │ 부하가 10개 샤드에 분산
   └ 1만 동접 30~60초 내 처리 가능
```

입장 처리 흐름:

1. 무작위 샤드 ID 선택 (0\~9)
2. 트랜잭션으로 10개 샤드 합산
3. 합산 < 정원 → 선택 샤드에 +1
4. 합산 ≥ 정원 → 차단 페이지로 이동

**한계**: 합산 결과가 stale 가능 → 정원 ±5% 초과 가능. 정확한 cutoff 은 운영적으로 미보장.

### 3.3 트래픽 폭증 안전 마진

* 매체사 푸시 등으로 동접이 5만\~10만으로 폭증할 가능성 고려
* 분산 샤드 카운터는 10 샤드로 유지 (1만 기준 최적이지만 5만\~10만까지 견딜 수 있는 마진)
* Firestore·Hosting 은 자동 스케일링이므로 폭증 시 자동 대응
* 폭증 시 비용은 추정의 약 5배 (월 \~$25\~$50)

### 3.4 부하 테스트 시나리오

* 단계 상승: 1k → 5k → 1만 → 폭증 시뮬(5만)
* 측정 항목: 정원 게이트 트랜잭션 충돌율, 라운드 동시 선택 처리율, broadcast 지연 (페이즈 변경 → 클라 수신)
* 도구: k6, Artillery 중 택 1

## 4. 게임 자동 진행 구현 방식

라운드 페이즈 (waiting → countdown → select → reveal → 다음 라운드 또는 종료) 자동 전환을 어떻게 구현할지 결정 필요.

### 4.1 옵션 비교

| 방식 | 동작 원리 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. Cloud Tasks**  | Cloud Function 이 다음 페이즈 호출을 큐에 예약, 시각 도달 시 큐가 함수 자동 호출  | 정확한 시각 보장, 재시도·모니터링 자동, 라운드 시간 가변 OK  | 큐 셋업 작업 필요  |
| B. Cloud Scheduler  | Cron 식 정기 호출 등록  | 단순  | 라운드 시간 가변이면 부적합, 분 단위 정밀도 한계  |
| C. setTimeout (함수 내부)  | 함수 실행 중 setTimeout 으로 다음 페이즈 트리거  | 별도 인프라 불필요  | 함수 실행 시간 한계(9분), 재시도 미보장, 함수 종료 시 타이머 소실  |
| D. 클라이언트 트리거  | revealAt 시각 도달 시 클라가 advanceRound 호출  | 별도 인프라 불필요  | 클라 신뢰 불가, 다중 호출·봇 호출 위험  |
| E. 하이브리드 (D + idempotency)  | 클라가 시각 도달 시 호출 + Cloud Function 이 phase 락으로 중복 차단  | 인프라 단순  | 1만 클라 동시 호출 시 함수 호출 비용 증가  |
