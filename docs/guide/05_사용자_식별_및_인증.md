# 5. 사용자 식별 및 인증

> 광고 참여 후 NBT 오퍼월 인앱웹뷰로 이벤트 페이지에 진입한 사용자를 어떻게 식별하고, Firebase Anonymous Auth 와 URL 쿼리 파라미터가 각각 어떤 역할을 맡는지 정의한다.
>
> - **다루는 것** — 인앱웹뷰 진입 흐름, 익명 Auth 역할, URL 쿼리 파라미터 5종의 의미, 식별자 혼동 방지 원칙
> - **위임하는 것** — 컬렉션·필드·보안 규칙 코드, 중복 참여 선점 저장소, 정원·재진입 정책, 함수 내부 구현, 운영자 지급 업무
> - **상위 문서** — 프로젝트 배경과 범위는 [1. 프로젝트 개요](./01_프로젝트_개요.md), 전체 요청 흐름은 [4. 시스템 아키텍처](./04_시스템_아키텍처.md) 를 따른다

---

## 5.1 이 문서의 역할

> **핵심 원칙 (먼저 읽기)**
>
> - URL `uid` ≠ Firebase Auth UID. 문서에서는 URL `uid` 를 `adisonUid` 로 부른다.
> - 중복 참여 차단의 기준 키는 `click_key` 가 아니라 `adisonUid` 다.
> - Firebase Anonymous Auth 는 본인 권한 확인용이지, 중복 차단용이 아니다.

**식별자 한 줄 요약**

| 식별자 | 한 줄 역할 |
|---|---|
| Firebase Auth UID | 본인 권한 확인 (내부 인증) |
| `adisonUid` (URL `uid`) | 사용자 구분 + 중복 차단 기준 키 |
| `advertisingId` | 사용자 구분 보조값 |
| `clickKey` | 우승자 수동 지급 확인용 (중복 차단 ✕) |
| `pubCode` / `pubAppCode` | 진입 매체사·앱 구분 |

자세한 의미와 정책은 5.3 이후에서 다룬다.

- **목적** — 이벤트 페이지에 들어온 사용자가 누구인지 판별하기 위해 어떤 식별자를 받고, 어떤 식별자는 내부 인증·권한에 쓰며, 어떤 식별자는 지급 확인에 쓰는지 한 곳에 고정한다.
- **범위** — 사용자 식별과 인증의 개념·역할을 다룬다. 실제 Firestore 스키마, 보안 규칙 코드, 중복 참여 차단 트랜잭션은 다른 챕터로 위임한다.
- **위임 대상**

| 항목 | 위임 챕터 |
|---|---|
| 참가자 문서, 중복 참여 선점 저장소, 결과 요약 문서의 최종 경로·필드·보안 규칙 코드 | 6장 데이터 모델 및 보안 정책(작성 예정) |
| 중복 참여 선점, 정원 게이트, 재진입·이탈 처리 | 7장 동시성·정원·중복참여 정책(작성 예정) |
| `joinGame` 파라미터 정규화·검증·트랜잭션 구현 | 8장 자동진행 및 서버리스 함수(작성 예정) |
| 우승자 확인, 수동 지급, 운영자 처리 절차 | 10장 운영 정책 및 관리자 업무(작성 예정) |
| 개인정보 고지 문구 확정, 미결정 정책 | 13장 리스크·미결정사항·다음 단계(작성 예정) |

## 5.2 진입 및 인증 흐름

사용자는 공유 링크나 일반 브라우저 직접 진입이 아니라, **광고 참여 후 NBT 오퍼월 인앱웹뷰가 이벤트 페이지를 띄우는 흐름**으로 진입한다.

```text
광고 참여 완료
  → NBT 오퍼월 인앱웹뷰가 /event?... 오픈
  → 클라이언트가 Firebase Anonymous Auth 로그인
  → 클라이언트가 URL 쿼리 파라미터 5종으로 joinGame 호출
  → 서버가 request.auth.uid 와 파라미터 정규화/검증
  → 입장 가능 여부, 중복 참여, 정원 정책으로 위임
```

흐름별 책임은 다음과 같다.

| 단계 | 주체 | 책임 |
|---|---|---|
| 광고 참여 완료 | NBT 오퍼월 | 이벤트 페이지를 열 수 있는 진입 컨텍스트 생성 |
| 이벤트 페이지 오픈 | NBT 오퍼월 인앱웹뷰 | `/event` 경로에 URL 쿼리 파라미터 5종을 붙여 페이지 표시 |
| 익명 로그인 | 클라이언트 | Firebase Anonymous Auth 로 내부 인증 식별자인 Auth UID 발급 |
| 입장 요청 | 클라이언트 | URL 파라미터 5종을 payload 로 전달하고, 인증된 Callable 요청으로 `joinGame` 호출 |
| 검증·입장 처리 | Cloud Functions | `request.auth.uid` 에서 Auth UID 를 확인하고, 파라미터 정규화/검증 후 입장 가능 여부를 트랜잭션으로 처리 |

`/event` 에 필수 파라미터가 없거나 형식이 유효하지 않으면 정상 입장으로 보지 않는다. 누락·오류 처리의 화면 정책은 라우팅/UX 문서에서, 서버 거부 응답의 세부 코드는 8장에서 다룬다.

## 5.3 URL 쿼리 파라미터 5종

광고 참여 후 이벤트 페이지로 이동할 때 다음 5개 쿼리 파라미터를 전달받는다.
이 표는 NBT 오퍼월에서 전달되는 파라미터 이름과 문서 내 의미를 고정한다. 각 값을 저장할 최종 문서 경로와 필드명은 6장에서 확정한다.

| 파라미터 | 문서 내 명칭 | 역할 | 사용 원칙 |
|---|---|---|---|
| `uid` | `adisonUid` | 사용자 구분용 Adison 유저 식별자 | Firebase Auth UID 와 구분해 설명한다. 중복 참여 차단의 기준 식별자로 사용한다 |
| `advertising_id` | `advertisingId` | 사용자 구분 보조값으로 쓰는 디바이스 광고 ID | `uid` 와 함께 사용자 확인 보조 정보로 사용한다 |
| `click_key` | `clickKey` | 수동 지급 확인용 키 | 우승자 수동 지급 확인에 사용한다. 클릭마다 바뀔 수 있으므로 중복 차단 키로 쓰지 않는다 |
| `pub_code` | `pubCode` | 진입 매체사 구분 코드 | 어떤 매체사 경로로 들어왔는지 구분하는 값으로 사용한다 |
| `pub_app_code` | `pubAppCode` | 진입 매체사 앱 구분 코드 | 빈 값일 수 있으나, 전달된 값은 매체사 앱 구분에 사용한다 |

핵심 구분은 다음과 같다.

- URL `uid` 는 Firebase Auth UID 가 아니다. 문서에서는 혼동을 피하기 위해 URL `uid` 를 **`adisonUid`** 로 풀어 쓴다.
- Firebase Auth UID 는 내부 인증·권한 확인용 식별자로 사용한다. 이 값을 어떤 문서 ID 또는 필드에 연결할지는 6장에서 확정한다.
- `click_key` 는 지급 확인용이지 중복 참여 차단용이 아니다.
- `pub_code`, `pub_app_code` 는 사용자 본인 식별보다 **진입 매체사 구분**에 초점을 둔다.

## 5.4 Firebase Anonymous Auth 역할

Firebase Anonymous Auth 는 사용자의 실명·회원 계정을 받기 위한 장치가 아니라, Firestore 보안 규칙과 서버 검증에서 사용할 **내부 인증 식별자**를 발급하기 위한 장치다.

| 항목 | 역할 |
|---|---|
| Firebase Auth UID | 본인 권한 확인 기준. 최종 저장 경로와 문서 ID 사용 여부는 6장에서 확정 |
| `request.auth.uid` | Callable Function 과 보안 규칙에서 요청 주체를 확인하는 값 |
| URL `uid` / `adisonUid` | Adison 사용자 구분값. Firebase Auth UID 와 별개 |

Anonymous Auth 를 사용하는 이유는 다음과 같다.

- 클라이언트가 임의의 사용자 ID를 주장하더라도 서버는 `request.auth.uid` 로 실제 호출 주체를 확인할 수 있다.
- 본인 참가자 문서만 읽도록 제한하는 보안 규칙의 기준을 만들 수 있다.
- 외부 회원가입 없이 이벤트 참여 흐름을 단순하게 유지할 수 있다.

단, Anonymous Auth UID 만으로 중복 참여를 막지는 않는다. 사용자가 브라우저 상태를 초기화하거나 다른 기기에서 들어오면 새 Auth UID 가 발급될 수 있다. 따라서 중복 참여 차단은 URL `uid` 기반 선점 정책으로 위임한다.

## 5.5 사용자 식별 기준과 중복 차단 위임

본 프로젝트에는 서로 다른 목적의 식별자가 공존한다.

| 목적 | 기준 식별자 | 설명 |
|---|---|---|
| 본인 권한 확인 | Firebase Auth UID | 현재 요청자가 어떤 참가자 상태의 주체인지 확인 |
| 사용자 구분 | `uid`, `advertising_id` | 매체 측 사용자와 디바이스 광고 ID 를 통해 사용자를 구분 |
| 중복 참여 차단 | `uid` 기반 정규화/해시 값 | 같은 매체 사용자가 여러 번 입장하지 못하도록 서버 트랜잭션에서 선점 |
| 수동 지급 확인 | `click_key` | 우승 후 운영자가 지급 확인에 참고하는 외부 키 |
| 진입 매체사 구분 | `pub_code`, `pub_app_code` | 어떤 매체사·앱 경로로 들어왔는지 구분 |

중복 참여 차단은 `click_key` 가 아니라 `uid` 기준으로 한다. `click_key` 는 같은 사용자라도 광고 클릭이나 진입 시점마다 달라질 수 있다. 따라서 중복 차단 키로 쓰면 동일 사용자의 재진입을 놓칠 수 있다.

`uid` 기반 선점 저장소의 최종 경로와 문서 키, 정규화 규칙, 트랜잭션 처리, 재진입·이탈 시 탈락/차단 정책은 6장 데이터 모델 및 보안 정책과 7장 동시성·정원·중복참여 정책에서 정의한다.

## 5.6 개인정보/고지 관점

Firebase Auth UID, URL `uid`, `advertising_id`, `click_key` 는 단독으로는 식별성이 약하다. 다만 운영자가 보유한 외부 데이터와 결합되면 개인 식별 또는 지급 대상자 확인에 쓰일 수 있다. 따라서 이벤트 진입·참여 화면에서 각 식별자의 사용 목적을 사용자에게 고지하는 것을 전제로 한다 (Auth UID = 본인 상태 접근, `uid`/`advertising_id` = 사용자 구분, `click_key` = 수동 지급 확인, `pub_code`/`pub_app_code` = 매체 구분).

개인정보 동의 문구의 최종 문안, 보관 기간, 삭제 정책은 본 문서에서 확정하지 않는다. 정책 확정이 필요한 항목은 13장 미결정사항으로 관리한다.

## 5.7 예외 경로와 위임

| 상황 | 처리 방향 | 위임 챕터 |
|---|---|---|
| 필수 URL 파라미터 누락 | 정상 입장 거부. 사용자에게 유효하지 않은 진입 안내 | 6장, 8장 |
| `advertising_id` 또는 `pub_app_code` 가 비어 있음 | 허용 여부와 기본값은 서버 검증 정책으로 고정 | 6장, 8장 |
| 같은 `uid` 로 재진입 | 중복 참여 선점 기준으로 중복 참여 또는 재진입 정책 적용 | 7장 |
| 같은 Firebase Auth UID 로 재호출 | 현재 게임 상태와 기존 참가자 상태에 따라 재입장/탈락/거부 정책 적용 | 7장 |
| `click_key` 가 바뀐 재진입 | 중복 차단 기준은 `click_key` 가 아니라 `uid` 이므로 `uid` 기준 정책 적용 | 7장 |
| 우승자 지급 확인 | `click_key` 와 사용자 구분값을 운영자가 확인해 수동 지급 | 10장 |
| 개인정보 고지 문구 미확정 | 미결정사항으로 등록 후 PM/운영 합의 | 13장 |
