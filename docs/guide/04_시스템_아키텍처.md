# 4. 시스템 아키텍처

> 가위바위보 챌린지가 어떤 Firebase 서비스 조합으로 동작하고, 요청이 어떤 경로로 흐르며, 어떤 원칙이 설계를 묶어 두는지를 정의한다.
>
> - **다루는 것** — Firebase 서비스 구성, 요청 흐름, 단일 쓰기 진입점 원칙, 클라이언트 구독 전략과 fan-out 비용 형태, 규모별 권장 구성
> - **위임하는 것** — 데이터 모델 필드, 보안 규칙 코드, 동시성 구현, 자동 진행 내부 메커니즘, 호스팅 설정, 비용 수치 (각 전담 챕터로)
> - **상위 문서** — 프로젝트 배경과 범위는 [1. 프로젝트 개요](./01_프로젝트_개요.md), 페이즈 상태 머신과 라운드 흐름은 [3. 게임 룰 및 라운드 흐름](./03_게임_룰_및_라운드_흐름.md) 을 따른다

## 4.1 이 문서의 역할

- **범위** — "어떤 서비스가 무슨 역할을 하고, 요청이 어떤 경로로 흐르는가" 수준만 다룬다. 필드 정의, 보안 규칙 코드, 분산 카운터 구현, 큐 설정, 비용 수치는 다른 챕터로 위임한다.
- **위임 대상**

## 4.2 설계 원칙

본 시스템의 아키텍처는 다음 다섯 가지 원칙 위에 서 있다. 필드 단위 메커니즘은 각 전담 챕터에 위임하고, 4장은 아키텍처 수준 원칙만 정의한다.

- **클라이언트 신뢰 금지** — 승패 판정, 탈락 처리, 우승자 확정, 경품 지급 상태 변경은 모두 서버(Cloud Functions)에서만 수행한다.
    - 클라이언트가 보낸 마감 시각·라운드 번호·UID 도 그대로 신뢰하지 않고 서버 timestamp 와 `request.auth.uid` 로 재검증한다.
- **단일 서버 쓰기 게이트웨이** — 모든 도메인 쓰기는 서버 함수만 수행한다.
    - 클라이언트 직접 호출은 Callable API 로 제한하고, 라운드 종료·배치 판정은 Cloud Tasks/Pub/Sub 같은 내부 트리거로 분리한다. Firestore 보안 규칙은 클라이언트 직접 쓰기 전체 차단(`allow write: if false`)을 기본으로 둔다.
- **공개·비공개 분리** — 모든 사용자가 읽을 수 있는 공개 상태에는 외부 지급 식별자나 개인정보를 두지 않는다.
    - 우승자 Adison 식별자와 경품 수령용 개인정보는 권한 제한 영역으로 분리한다.
- **본인 상태만 실시간 구독, 공통 상태는 폴링** — 본인 생존·탈락 상태만 실시간 구독하고 공통 상태는 5초 내외로 폴링해 업데이트 fan-out 을 피한다.
    - 폴링도 사용자 수에 비례해 read 가 발생하지만, 문서 갱신 횟수와 read fan-out 을 분리해 `사용자 수 × 문서 수 × 폴링 주기` 로 비용을 예측할 수 있게 한다.
- **모든 페이즈 전환은 트랜잭션으로 atomic 보장** — 입장·라운드 시작·라운드 종료·우승 확정 등 상태 전이는 트랜잭션 안에서 검사·갱신을 한 번에 처리해 중복 실행과 부분 갱신을 차단한다.
    - 페이즈별 트랜잭션의 구체 정책 표는 8장에서 다룬다.

## 4.3 Firebase 서비스 구성

본 프로젝트는 백엔드 신규 개발 없이 Firebase 매니지드 서비스 조합만으로 1만 명 규모를 처리하는 것을 목표로 한다.

### 스택 구성

```
[React SPA]              ← Firebase Hosting (정적 파일 + CDN)
    ↓
[Authentication]         ← 익명 로그인 (Anonymous Auth)
    ↓
[Cloud Functions]        ← 입장 검증, 페이즈 전환, 승패 판정 (단일 쓰기 진입점)
    ↑   ↓                       ↑
    │   ↓                  [Cloud Tasks]  ← 라운드 시각 도달 시 beginSelect/endRound 호출
    │   ↓                       │
    │   ↓                  [Pub/Sub]      ← 1만 명 판정 분산 dispatch
    │   ↓                       │
    │   └───────────────────────┘
    ↓
[Firestore]              ← 모든 도메인 데이터 저장 (게임/플레이어/라운드/결과)
```

### 서비스별 역할

| 서비스 | 역할 |
|---|---|
| **`Firebase Hosting`** | React SPA 빌드 결과물의 정적 배포와 CDN. SSR 불필요한 SPA 구성에 적합 |
| **`Authentication`** | 익명 UID 자동 발급. 보안 규칙의 `request.auth.uid` 검증 기반 제공 |
| **`Cloud Functions`** | 모든 도메인 쓰기의 단일 진입점. 입장·선택·라운드 시작·종료·배치 판정·우승자 정보 제출을 담당 |
| **`Cloud Tasks`** | 카운트다운 종료 시각의 `beginSelect` 와 선택 종료 시각의 `endRound` 를 정확히 호출하기 위한 동적 예약 큐. 멱등성을 위한 결정적 task name 지원 |
| **`Pub/Sub`** | 1만 명을 한 함수에서 처리하지 않고 1000명 단위 배치로 분산 dispatch 하는 파이프라인 |
| **`Firestore`** | 모든 영구 데이터 저장. 공개 상태와 비공개 상태를 데이터 영역 단위로 분리 |

## 4.4 요청 흐름

코드는 8장에서 다루고, 본 절은 "어느 컴포넌트가 무엇을 하는가"만 정의한다.

### (a) 입장 흐름

1. 광고 참여로 인앱 웹뷰가 이벤트 페이지를 띄우면 클라이언트는 익명 Auth 로 로그인해 Firebase UID 를 발급받는다.
2. 클라이언트가 URL 쿼리 파라미터(`click_key`/`uid`/`advertising_id`/`pub_code`/`pub_app_code`)와 닉네임을 담아 Callable `joinGame` 을 호출한다.
3. 함수는 `request.auth.uid` 로 사용자 식별을 확인하고, 쿼리 파라미터를 서버에서 다시 정규화한다.
4. 트랜잭션 안에서 게임 상태, 마감 시각, 정원을 검증한다.
5. 같은 트랜잭션에서 Adison `uid` 선점으로 중복 참여를 차단하고, 플레이어 상태 생성과 생존자 카운터 갱신을 함께 처리한다.
6. 결과를 클라이언트에 반환한다. 정원·중복 참여·재진입의 구체 메커니즘은 7장에서 다룬다.

### (b) 선택 제출 흐름

1. `select` 페이즈에서 클라이언트가 가위·바위·보 중 하나를 골라 Callable `submitChoice` 를 호출한다.
2. 함수는 `request.auth.uid` 로 본인 여부를 확인하고, 플레이어의 생존 상태·현재 라운드·마감 시각을 서버 기준으로 검증한다.
3. 검증 통과 시 본인 플레이어 상태에 선택값과 선택 라운드 정보를 갱신한다. 라운드별 1만 건 초기화 write 를 피하기 위한 구체 필드 정책은 6장을 따른다.

### (c) 라운드 자동 진행·종료 흐름

1. 라운드 시작 시 `startRound` 가 `countdown` 라운드 문서를 만들고 Cloud Tasks 에 결정적 task name 으로 `beginSelect` 를 선택 시작 시각에 예약한다.
2. 선택 시작 시각이 도달하면 Cloud Tasks 가 `beginSelect` HTTP 함수를 호출해 `select` 로 전이하고, 같은 트랜잭션 이후 `endRound` 를 선택 종료 시각에 예약한다.
3. 선택 종료 시각이 도달하면 Cloud Tasks 가 `endRound` HTTP 함수를 호출한다.
4. `endRound` 는 트랜잭션으로 현재 게임 상태와 라운드가 일치하는지 확인한 뒤 결과 공개 단계로 전이한다. 이 가드로 중복 호출이 와도 한 번만 실제 처리가 일어난다(멱등성).
5. 같은 함수가 라운드 시점의 생존자 범위를 batch manifest 로 고정하고, 각 batch 를 Pub/Sub 토픽으로 분산 dispatch 한다. 이렇게 고정해 두면 처리 도중 상태 변경으로 페이지 결과가 흔들리지 않는다.
6. `processBatch` 가 1000명 단위로 본인 선택과 서버가 무작위로 결정한 애디슨 손을 비교해 탈락·생존을 판정하고, 탈락자 입장 시점 샤드 기준으로 생존자 카운터를 차감한다. 같은 batch 가 재시도로 두 번 도착해도 배치 멱등성 문서로 한 번만 반영된다.
7. 모든 batch 가 완료되면 라운드 결과 집계와 게임 공개 상태 캐시가 갱신된다. 구체 필드명은 6장에서, 큐 설정·재시도·멱등성 상세는 8장에서 다룬다.

## 4.5 단일 서버 쓰기 게이트웨이

본 시스템은 도메인 쓰기를 Firestore 보안 규칙으로 직접 허용하지 않는다. 대신 모든 입장·선택·페이즈 전환·우승자 처리를 **서버 함수**를 통해서만 수행한다.

이렇게 하면 라운드·생존·마감·UID 위장 같은 검증을 보안 규칙 헬퍼로 중복 작성할 필요가 없고, 보안 규칙은 "공개 read 가 가능한 문서만 열고 클라이언트 write 는 전부 차단" 하는 단순 차단 위주 구성으로 정리된다.

Firestore 규칙은 클라이언트 직접 쓰기를 기본 차단(`allow write: if false`)한다. 규칙 코드와 필드별 권한 정의는 6장을 따른다.

서버 함수 표면은 호출 주체에 따라 분리한다. 클라이언트가 직접 호출할 수 있는 것은 Callable API 뿐이며, 라운드 종료·배치 판정 같은 내부 작업자는 Cloud Tasks 또는 Pub/Sub 같은 서버 트리거만 실행한다.

### 클라이언트 Callable API

| 함수 | 역할 |
|---|---|
| **`joinGame`** | 쿼리 파라미터 정규화·Adison `uid` 중복 차단·정원 검증 후 입장 상태 생성과 카운터 갱신을 트랜잭션으로 처리 |
| **`submitChoice`** | 본인 여부·현재 라운드 일치·마감 전 여부를 검증한 뒤 본인 선택 상태를 갱신 |
| **`submitWinnerInfo`** | 우승자 본인이 경품 수령용 개인정보를 1회만 제출하도록 검증 후 비공개 수령 정보 영역에 저장 |

### 서버 내부/백그라운드 함수

| 함수 | 호출 주체 | 역할 |
|---|---|---|
| **`startRound`** | 운영자/서버 내부 트리거 | `countdown` 라운드 문서와 선택 시작 시각을 설정하고 Cloud Tasks 에 `beginSelect` 예약 |
| **`beginSelect`** | Cloud Tasks HTTP 호출 | `select` 로 전이하며 선택 마감 시각을 설정하고 Cloud Tasks 에 `endRound` 예약 |
| **`endRound`** | Cloud Tasks HTTP 호출 | 트랜잭션으로 결과 공개 단계 전이를 멱등 처리한 뒤 batch 범위를 고정하고 Pub/Sub 으로 분산 dispatch |
| **`processBatch`** | Pub/Sub 메시지 | 1000명 단위로 승패 판정·탈락 처리·샤드 카운터 차감을 수행하고 배치 멱등성 상태를 갱신 |

각 함수의 매개변수·반환 타입·인증 방식·구현 코드는 본 문서 범위가 아니다. 자동 진행 함수의 내부 구현은 8장, 보안 규칙과 필드별 권한은 6장을 따른다.

## 4.6 클라이언트 구독 전략과 fan-out 비용

1만 명 규모에서는 "누가 무엇을 어떻게 구독하는가" 가 곧 비용·부하의 형태를 결정한다. 본 시스템은 본인 데이터에만 실시간 구독을 쓰고, 공통 상태는 폴링으로 처리하는 비대칭 전략을 채택한다.

본인 플레이어 상태는 `onSnapshot` 으로 실시간 구독한다. 본인의 생존·탈락 전이는 즉시 화면에 반영되어야 하고, 한 유저당 한 상태만 구독하므로 공통 문서 fan-out 이 발생하지 않는다.

게임 공통 상태와 라운드별 공개 집계는 5초 내외 간격으로 폴링한다. 두 방식의 비용 형태는 다음과 같이 다르다.

**`onSnapshot` 의 비용 형태** — 공통 문서가 갱신될 때마다 구독자 수만큼 즉시 read fan-out 이 발생한다. 예를 들어 라운드 결과 문서 1회 갱신 × 1만 listener 는 즉시 1만 read 로 이어지며, 갱신이 잦을수록 부담이 누적된다.

**폴링의 비용 형태** — 갱신 횟수와 무관하게 **사용자 수 × 문서 수 × 폴링 주기**에 비례해 read 가 발생한다. 예를 들어 1만 명이 공통 문서 1개를 5초마다 읽으면 분당 약 12만 read 다. 비용 형태가 결정적이라 예측이 쉽다는 점이 이점이며, 절대 수치와 시나리오별 추정은 11장에서 다룬다.

관전 모드는 다른 플레이어의 개별 정보를 읽지 않는다. 관전 화면은 라운드별 집계값과 현재 생존자 수 같은 공개 상태만 사용해 구성하며, 다른 플레이어의 닉네임이나 선택은 노출하지 않는다. 구체 필드명과 공개 캐시 컬렉션 구조는 6장에서 정의한다.

## 4.7 규모별 구성 비교

본 절은 "왜 이 프로젝트가 Firestore + 분산 샤드 카운터 조합에 머무는가" 를 규모 관점에서 정리한다.

| 규모 | 권장 구성 | 비고 |
|---|---|---|
| ~1k | Firestore 단독 | 기본 설정만으로 충분, 샤딩 불필요 |
| **1k~1만** | **Firestore + 분산 샤드 카운터 (10개)** | **본 프로젝트 목표 구간** |
| 1만~10만 | Firestore + RTDB 하이브리드 | fan-out 최적화 추가 필요 |
| 10만+ | 전용 게임 서버 검토 | Firebase 단독 한계 |

본 프로젝트는 1만 명 동시 접속을 상한으로 본다. 이 구간에서는 단일 카운터 문서의 쓰기 한도가 병목이 되므로 생존자 카운터를 10개 샤드로 분산해야 하지만, RTDB 하이브리드까지는 필요 없다. fan-out 비용은 본인 상태 onSnapshot + 공통 상태 폴링 패턴(4.6)으로 평탄화한다.

상위 구간(1만~10만 이상)으로 트래픽이 갑자기 늘어나는 시나리오는 Firestore·Hosting 자동 스케일이 흡수해 주지만 비용이 비례 증가한다. 자동 스케일 기준 비용 추정과 트래픽 폭증 대비 시나리오는 11장에서 다룬다. 분산 카운터 구현 자체와 정원 게이트 정책은 7장을 따른다.
