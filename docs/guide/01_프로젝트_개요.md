# 1. 프로젝트 개요

> 가위바위보 챌린지 — **애디슨 vs 유저 구도의 실시간 토너먼트 이벤트** 를 백엔드 신규 개발 없이 프론트엔드 + Firebase 만으로 구현하는 MVP. 전체 챕터의 진입 문서다.

---

## 1.1 프로젝트 정의

- **무엇을** — 매체사(예: PURSE)에서 진입한 1만 명 규모의 사용자가 동시에 참여하는 **가위바위보 토너먼트 이벤트**.
- **왜** — 백엔드 신규 개발 없이 PRD 핵심 기능을 만족할 수 있는지 검증하기 위한 MVP. 가능하면 동일한 패턴을 향후 다른 챌린지 이벤트에도 재사용한다.
- **어떻게** — Firebase (Hosting + Firestore + Cloud Functions + 익명 Auth + Cloud Tasks) 기반 React SPA.

> 1차 기술 검토 결론 — *"수행 가능. Firebase + Cloud Functions 만으로 PRD 핵심 기능 구현 가능해보임."*

---

## 1.2 게임 룰

- **애디슨 vs 유저** 구도의 가위바위보 토너먼트.
- 애디슨에게 **이긴 사람만 다음 라운드 진출**, **비기거나 진 사람은 탈락**.
- **최후 1인** 이 남을 때까지 진행. 전원 탈락 시 다음 회차로 이월.
- 라운드는 **N분 간격으로 자동 진행**.
- **1등 경품은 운영자 수동 지급**. 우승자 식별자만 자동 기록한다.

---

## 1.3 시스템 한 눈에 보기

```
[React SPA]              ← Firebase Hosting (정적 파일 + CDN)
    ↓
[Authentication]         ← 익명 로그인 (Anonymous Auth)
    ↓
[Cloud Functions]        ← 입장 검증, 페이즈 전환, 승패 판정 (단일 쓰기 진입점)
    ↓                       ↑
    ↓                  [Cloud Tasks]  ← 라운드 자동 진행 (운영 단계 도입 예정)
    ↓
[Firestore]              ← 모든 데이터 저장 (게임/플레이어/라운드/결과)
```

라운드는 `waiting → countdown → select → reveal → 다음 라운드 / ended` 페이즈로 진행한다.

- **클라이언트** 는 본인 상태와 공통 게임 상태를 실시간 구독해 페이즈·라운드 변화를 수신한다.
- **서버 로직(Cloud Functions)** 은 입장·선택·우승자 정보 제출은 Callable API 로 받고, 페이즈 전환·승패 판정은 Cloud Tasks HTTP / Pub/Sub 내부 트리거로 처리한다. 모든 Firestore 도메인 쓰기는 서버 함수 게이트웨이를 통해 트랜잭션·멱등성으로 보호한다.
- **자동 진행** 은 검증 단계엔 클라이언트 트리거 + 함수 멱등성으로 충분하고, 운영 단계엔 Cloud Tasks 로 정밀화한다.

---

## 1.4 목표 및 규모

| 항목 | 값 | 비고 |
|---|---|---|
| 목표 동시 접속 | **최대 1만 명** | 분산 샤드 카운터 10개로 처리 |
| 운영 빈도 | 일회성 또는 **월 4회** 정기 이벤트 | 합의된 가정값 |
| 1회 행사 비용 | **`$1` ~ `$2`** | 실측 아님, 추정 |
| 월 4회 비용 (prd 단독) | **`$5` ~ `$10`** | 〃 |
| 월 4회 비용 (dev + prd) | `$8` ~ `$15` | dev 는 테스트 트래픽만 |
| 트래픽 폭증(5만~10만) 대비 | 자동 스케일 + 비용 5배 (`$25` ~ `$100`/월) | Firestore·Hosting 자동 스케일 |

## 1.5 범위

### 포함 (이번 MVP 목표)

| # | 항목 | 비고 |
|---|---|---|
| 1 | 동시 접속 / 인앱 웹뷰 랜딩 | 광고 참여 진입 |
| 2 | URL 쿼리 파라미터 5종 식별 | `uid`/`advertising_id`는 사용자 구분, `click_key`는 수동 지급, `pub_code`/`pub_app_code`는 진입 매체사 구분 |
| 3 | n초간 가위/바위/보 선택 | 라운드별 선택 시간 제한 |
| 4 | 컴퓨터 손 (글로벌·사전 미결정) | 라운드 종료 시점 서버 무작위 생성 |
| 5 | 이기면 진출 / 비기거나 지면 관전 | 생존 상태 기반 화면 분기 |
| 6 | 라운드별 생존 확률·묵찌빠 분포 노출 | 라운드 단위 집계 |
| 7 | 최후 1인 우승자 자동 기록 | 운영자 수동 적립 전 단계 |
| 8 | 전원 탈락 시 이월 표기 | 우승자 없음 종료 사유 분기 |
| 9 | 라운드 N분마다 자동 진행 | 시간 기반 자동화 |
| 10 | 정원 차면 접속 차단 | 분산 샤드 카운터로 동접 게이트 |
| 11 | 랜덤 닉네임 부여 | Adison 식별자와 분리된 표시용 닉네임 |

구현 진행 상태(완료 / 미구현 / 잔여)는 [2장 요구사항 및 구현 현황](./02_요구사항_및_구현현황.md) 참조.

### 제외 (PM 합의로 이번 범위 밖)

- 매체사별 분기, SNS 공유, RV/동영상 광고
- 100만원 자동 적립 — 우승자 식별 자동, 적립은 운영자 수동

---

## 1.6 주요 제약 및 운영 전제

- **Firebase Blaze 요금제 활성화 필수** — Cloud Functions·Cloud Tasks 등 유료 기능 사용 한도 확보.
- **React SPA + Firebase Hosting** — SSR 불필요, 정적 배포.
- **인앱 웹뷰 진입** — 광고 참여 시 NBT 네이티브 SDK가 인앱 웹뷰로 이벤트 페이지를 띄우면서 5종 쿼리 파라미터를 전달한다. `uid`/`advertising_id`는 사용자 구분, `click_key`는 수동 지급 확인, `pub_code`/`pub_app_code`는 진입 매체사 구분에 사용한다.
- **정원 ±5% 초과 허용** — 분산 샤드 카운터의 stale 합산 한계로 정확한 cutoff 은 운영적으로 미보장. 정원은 보수적으로 설정한다.
- **운영자 수동 적립** — 우승자 식별만 자동화하고 적립은 운영자가 수동 처리. 4회 한정으로 부담 작다는 PM 합의 위에 성립한다.
- **단일 서버 쓰기 게이트웨이** — 모든 도메인 쓰기는 Cloud Functions/Admin 서버 경로로만 수행한다. 클라이언트 직접 쓰기는 Callable API 로 제한하고, 라운드 전환·배치 판정은 Cloud Tasks HTTP / Pub/Sub 내부 트리거로 분리한다. Firestore 보안 규칙은 클라이언트 직접 쓰기 전체 차단이 기본.

---

## 1.7 용어집

| 용어 | 의미 |
|---|---|
| **NBT** | 자사 사용자 식별 시스템. 인앱 웹뷰로 진입하는 자사 SDK 환경 |
| **익명 Auth** | Firebase Anonymous Authentication. 무료·무제한, 보안 규칙 기반 제공 |
| **Cloud Tasks** | 페이즈 전환을 정해진 시각에 호출하기 위한 큐 (운영 단계 도입 예정) |
| **분산 샤드 카운터** | 단일 카운터 병목을 회피하는 10개 샤드 구성. 1만 동접 정원 게이트에 사용 |

매체 식별 키, 데이터 모델 필드, 결과 문서 등 데이터 모델 용어는 [6장 데이터 모델 및 보안 정책](./06_데이터_모델_및_보안_정책.md)에서 정의한다.
