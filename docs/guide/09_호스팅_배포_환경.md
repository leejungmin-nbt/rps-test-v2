> 가위바위보 챌린지가 어떤 호스팅 위에서 동작하고, dev 와 prd 가 어떻게 분리되며, Cloud Tasks·Pub/Sub·Functions 의 GCP 권한과 service account 가 어떻게 발급되는지를 정의한다.

## 9.2 설계 원칙

본 장의 모든 결정은 다음 여섯 원칙 위에서 성립한다. 원칙은 추상적 선언이 아니라 9.3 ~ 9.12 의 구체 결정이 환원되는 근거다.

- **환경 4축 격리** — dev 와 prd 는 *Firebase 프로젝트, Cloud Tasks 큐, service account, 함수 URL* 네 축을 모두 분리한다. 한 축이라도 공유되면 cross-environment 호출 사고가 발생할 수 있다.
- **단일 쓰기 게이트웨이 일관성** — 4장의 단일 쓰기 게이트웨이 원칙은 환경에 무관하게 같다. dev 도 prd 와 같은 Callable / Cloud Tasks HTTP / Pub/Sub 표면을 가지며, 보안 규칙은 두 환경에서 동일한 차단 정책을 유지한다.
- **인프라 산출물의 결정성** — `firebase.json`, 보안 규칙 파일, 큐 정의, IAM 바인딩은 코드 저장소에서 관리한다. 콘솔 수동 변경은 운영 절차의 예외로만 허용하고 즉시 코드로 환원한다.
- **CDN 캐시 분리** — `index.html` 은 캐시되지 않고, 해시 파일명을 가진 정적 자산만 immutable 로 캐시한다. 인앱웹뷰가 stale 번들을 잡으면 NBT 쿼리 파라미터 5종 라우팅이 깨질 수 있기 때문이다.
- **OIDC 기본값** — Cloud Tasks → 함수 호출은 모두 OIDC 토큰 기반 인증이다. 함수 측은 토큰의 `serviceAccountEmail` 과 `audience` 를 두 축 모두 매칭한다. 둘 중 하나만 검증하는 절차는 8장 8.6.4 정본 위반이다.
- **비밀은 코드에 두지 않는다** — Firebase 클라이언트 config 같은 공개 식별자는 빌드 산출물에 포함될 수 있으나, service account key·서버 비밀·관리자 토큰은 Secret Manager 또는 Functions runtime secret 로만 주입한다.

## 9.3 호스팅 채택과 CDN·헤더 정책

### 9.3.1 채택 결과

본 장은 **Firebase Hosting** 을 채택한다. 4장 4.3 의 서비스 구성 정본을 그대로 따르며, 다음 네 조건을 만족하는 유일한 옵션이기 때문이다.

- React SPA 의 정적 빌드 산출물을 그대로 배포할 수 있어야 한다(SSR 불필요).
- `asia-northeast3` 리전의 Firebase Functions 와 같은 GCP 프로젝트 안에서 IAM·service account·로깅을 공유해야 한다.
- 도메인·SSL·CDN 이 추가 운영 인프라 없이 자동 제공되어야 한다.
- 인앱웹뷰 진입(5장 5.2) 의 단발 트래픽 구간에서도 안정적으로 정적 자산이 내려가야 한다.

App Hosting 은 SSR 지원이라는 강점이 있으나 본 시스템은 SPA 구성이므로 채택 이유가 없다. Vercel·사내 인프라 등 외부 호스팅은 Firebase 프로젝트와 IAM·로깅·service account 가 분리되어 단일 쓰기 게이트웨이 일관성 원칙을 깨므로 채택하지 않는다.

### 9.3.2 CDN 캐시 정책

Firebase Hosting 은 자동 CDN 을 제공하지만, 캐시 헤더 정책을 잘못 잡으면 인앱웹뷰가 stale 번들을 받는 사고가 생긴다. 본 장은 다음 두 계층으로 캐시를 분리한다.

| 자원 종류 | 캐시 정책 | 근거 |
|---|---|---|
| `index.html` | no-cache 또는 짧은 TTL | 매 진입마다 최신 SPA 진입점을 받아야 한다. 새 빌드의 정적 자산 해시 매핑이 깨지면 라우팅이 깨진다 |
| 해시 파일명을 가진 JS·CSS·이미지 | immutable, 장기 캐시 | 파일명에 빌드 해시가 포함되므로 내용이 바뀌면 새 파일명이 된다. 같은 파일명이면 영원히 같은 내용이라는 가정이 성립한다 |
| 해시 없는 정적 자산(예: 매체사 로고) | 짧은 TTL 또는 ETag 기반 재검증 | 파일명이 같지만 내용이 바뀔 수 있어 immutable 로 두면 안 된다 |

`index.html` 의 정확한 TTL 구체 값(0초 / 60초 / 300초 등)은 13장 미결정 큐로 둔다.

### 9.3.3 SPA rewrite

`/event` 진입 등 모든 라우트는 단일 `index.html` 로 rewrite 된다. 이는 React Router 가 클라이언트 측에서 라우팅을 수행하는 SPA 구성에서 표준 패턴이며, 인앱웹뷰가 어떤 경로로 페이지를 띄우든 `index.html` 이 응답되어야 5장 5.2 진입 흐름이 동일하게 동작한다.

SPA 진입 후 `clickKey`·`adisonUid` 등 URL 쿼리 파라미터 5종은 클라이언트 페이로드로 추출되어 `joinGame` 호출에 전달된다(5장 5.5). 호스팅은 이 파라미터를 가공하지 않고 그대로 통과시킨다.

`firebase.json` 의 rewrite 표현 자체는 9.5 의 항목 정본을 따른다.

## 9.4 환경 분리 모델

### 9.4.1 분리 옵션 비교

dev 와 prd 를 어떻게 분리할지는 PM 미정 항목이다. 본 장은 세 옵션을 검토 대상으로 두고, 최종 선택은 13장 미결정 큐로 위임한다.

| 옵션 | 동작 | 장점 | 한계 |
|---|---|---|---|
| (a) prd 단독 | Firebase 프로젝트 1개, 환경 변수 없이 운영 | 인프라·비용 최소 | 운영 중 실험·검증 불가, 부하 테스트가 prd 비용에 직접 영향 |
| (b) **dev + prd 두 프로젝트 (권장)** | Firebase 프로젝트 2개, 모든 4축(프로젝트·큐·SA·함수 URL) 분리 | 환경 격리 보장, 부하 테스트 안전, prd 변경 사고 차단 | 월 운영 비용 약간 증가, 배포 파이프라인 분기 필요 |
| (c) 단일 프로젝트 + 환경 변수 분기 | 같은 프로젝트 안에서 함수·큐 이름 prefix 로 환경 구분 | 인프라 단순 | service account·로그·IAM 가 섞여 cross-env 사고 위험, 9.2 의 4축 격리 원칙 위반 |

**무효화 사유** — 옵션 (c) 는 본 장의 환경 4축 격리 원칙과 정면으로 충돌한다.

- service account 가 한 프로젝트 안에 묶이면 dev 의 토큰이 prd 함수 URL 에 대해 합법화되는 분기가 생길 수 있다.
- 큐·로그·메트릭 라벨이 섞이면 운영 진단의 1차 신호(8장 8.10.4) 가 흐려진다.
- `games.phase` 전이를 다루는 큐 호출이 환경별로 격리되지 않으면 dev 의 `endRound` 시도가 prd 의 `reveal` 전이에 영향을 줄 수 있다.

옵션 (c) 채택 시 추가 가드(별도 SA 강제, audience 분리)를 모두 강제해야 옵션 (b) 와 동등한 안전성에 근접한다. 그 시점에는 단순성 이점이 사라지므로 옵션 (b) 가 사실상 우월하다.

### 9.4.2 환경 4축 격리

옵션 (b) 가 채택되면 다음 4축이 모두 환경별로 분리된다.

| 축 | dev | prd |
|---|---|---|
| Firebase 프로젝트 | dev 전용 프로젝트 ID | prd 전용 프로젝트 ID |
| Cloud Tasks 큐 | dev 프로젝트 안 `game-rounds` | prd 프로젝트 안 `game-rounds` |
| service account | dev 전용 SA(예: tasks-dispatcher) | prd 전용 SA |
| 함수 URL (audience) | dev 프로젝트의 `endRound` URL | prd 프로젝트의 `endRound` URL |

함수 측 OIDC 검증(9.6.3) 은 토큰의 `serviceAccountEmail` 이 *자기 환경의 SA* 와 일치하고, `audience` 가 *자기 환경의 함수 URL* 과 일치할 때만 호출을 수락한다. 이 두 검증을 모두 적용하면 환경 간 토큰 교차 사용이 자연 차단된다.

### 9.4.3 환경 식별 규칙

코드 안의 환경 식별은 명시적 환경 변수 한 가지(예: `ENV=dev | prd`) 로 분기한다. 클라이언트 빌드도 같은 키를 빌드 타임 변수로 받아 Firebase config 와 함수 region·project ID 를 결정한다. 환경 식별을 호스트명·콘솔 로그인 상태 등 묵시적 신호로 판단하는 분기는 도입하지 않는다 — 동일한 코드가 두 환경에서 다르게 동작할 위험이 있기 때문이다.

## 9.5 `firebase.json` 항목 정본

`firebase.json` 은 호스팅·함수·에뮬레이터 셋업의 단일 진입점 파일이다. 본 절은 본 시스템의 `firebase.json` 이 가져야 하는 항목과 결정 사항을 정본화한다. 실제 JSON 표현은 구현 PR 에서 작성한다.

### 9.5.1 hosting 섹션

| 항목 | 결정 |
|---|---|
| public | React 빌드 산출물 디렉터리 (예: `dist`). 환경별로 다르지 않게 둔다 |
| ignore | `firebase.json`, dotfiles, `node_modules` 를 모두 배제 |
| rewrites | 모든 경로를 `/index.html` 로 rewrite (SPA 라우팅) |
| headers — `index.html` | 9.3.2 정책에 따라 no-cache 또는 짧은 TTL |
| headers — 해시 정적 자산 | `Cache-Control: max-age=31536000, immutable` |
| headers — 해시 없는 자산 | 짧은 TTL 또는 ETag 기반 재검증 |
| cleanUrls / trailingSlash | 본 장에서는 결정하지 않음. 라우팅 정책 확정 시 13장 또는 라우팅 문서에서 정한다 |

### 9.5.2 functions 섹션

| 항목 | 결정 |
|---|---|
| source | 함수 코드 디렉터리 (예: `functions`) |
| runtime | Functions 플랫폼이 지원하는 LTS Node.js 버전 |
| region | `asia-northeast3` 고정 (4장 4.3 정본과 일치) |
| codebase | 단일 codebase 운영. 함수가 늘어나면 분리 검토는 13장 |

### 9.5.3 firestore 섹션

| 항목 | 결정 |
|---|---|
| rules | `firestore.rules` 파일을 가리킨다. 규칙 코드 정본은 6장 6.10 |
| indexes | `firestore.indexes.json` 파일을 가리킨다. 필요한 인덱스는 6장 컬렉션별 계약을 참고해 구현 단계에서 산출한다 |

### 9.5.4 emulators 섹션

| 항목 | 결정 |
|---|---|
| auth | 익명 Auth 모킹용으로 활성화 |
| firestore | 항상 활성화. 보안 규칙·인덱스 검증의 기본값 |
| functions | 활성화. Callable·HTTP·Pub/Sub 트리거 모두 모킹 |
| pubsub | 활성화. `process-batch` 토픽 모킹용 |
| hosting | 활성화. SPA rewrite 검증용 |
| ui | 활성화. 로컬 디버깅용 |

Cloud Tasks 는 Firebase Emulator 가 직접 지원하지 않는다. 본 장은 9.9.2 에서 우회 전략을 정의한다.

## 9.6 Cloud Tasks · Functions · Pub/Sub IAM 셋업

본 절은 8장 8.7 이 위임한 GCP 권한·service account·Functions IAM 바인딩 정본을 담는다. 큐의 *행위·멱등성*은 8장이 정본이고, 권한과 환경별 분기는 본 장이 정본이다.

### 9.6.1 service account 인벤토리

각 환경은 다음 service account (이하 SA) 를 가진다. SA 이름 자체는 운영 컨벤션을 따르되, 역할은 환경 간 동일하게 유지한다.

| SA 역할 | 권한 | 사용 위치 |
|---|---|---|
| Tasks Dispatcher | Cloud Tasks 의 `createTask` 권한, 호출 대상 함수에 대한 `roles/cloudfunctions.invoker` (또는 v2 의 Cloud Run invoker) | `startRound` / `beginSelect` 가 큐에 task 를 등록할 때, OIDC token 의 `serviceAccountEmail` 로 사용 |
| Pub/Sub Publisher | `process-batch` 토픽의 `roles/pubsub.publisher` | `endRound` 가 batch 메시지를 publish 할 때 사용 |
| Pub/Sub Subscriber Runtime | `processBatch` 함수의 실행 SA. Firestore read/write 권한 | `processBatch` 함수의 runtime identity |
| Functions Runtime (default) | Firestore admin 권한, 큐·토픽 권한은 위 두 SA 에 위임 | `joinGame` / `submitChoice` / `submitWinnerInfo` 의 runtime identity |

본 장은 SA 분리의 *원칙*을 고정한다. SA 의 정확한 이름·바인딩 명령은 운영 SOP 와 구현 PR 에서 정한다.

### 9.6.2 Functions IAM 바인딩

Cloud Tasks 가 호출하는 HTTP 함수(`beginSelect`, `endRound`) 는 인증된 호출만 허용한다.

| 함수 | invoker 허용 | 차단 |
|---|---|---|
| `beginSelect` | Tasks Dispatcher SA 만 | 그 외 모든 외부 호출 |
| `endRound` | Tasks Dispatcher SA 만 | 그 외 모든 외부 호출. 검증 단계에서만 8장 8.3.2 의 클라이언트 Callable 변형을 별도 함수로 둔다 |
| `processBatch` | Pub/Sub 만 (트리거 자체가 Pub/Sub) | 그 외 호출 표면 노출 금지 |

Callable 함수(`joinGame` / `submitChoice` / `submitWinnerInfo`) 는 Firebase SDK 의 표준 인증 흐름을 사용한다. 익명 사용자도 호출 가능하지만, 함수 내부에서 `request.auth.uid` 존재 여부를 검증한다(8장 8.6 계약).

### 9.6.3 OIDC 검증 절차

함수 측 OIDC 검증은 다음 두 축을 모두 매칭해야 8장 8.6.4 정본을 만족한다.

- **`serviceAccountEmail` 매칭** — 토큰을 발행한 SA 가 자기 환경의 Tasks Dispatcher SA 인지 확인한다. 다른 SA 가 발행한 토큰은 즉시 401 로 거부한다.
- **`audience` 매칭** — 토큰의 `audience` claim 이 자기 함수 URL 과 정확히 일치하는지 확인한다. dev 의 토큰이 prd URL 을 audience 로 발행되는 일은 없지만, 환경 4축 격리(9.4.2) 와 함께 두 번째 방어선으로 둔다.

검증 실패 시 응답은 `401 Unauthorized` 이며 본문에 진단 정보를 노출하지 않는다. 정상 응답이지만 8장 8.5 가드 불일치인 경우는 `200 + no-op` 으로 응답한다(8장 8.6.4 정본).

### 9.6.4 큐 설정 환경별 분기

8장 8.7 의 큐 설정 표는 환경에 무관하게 같은 값을 사용한다(이름 `game-rounds`, region `asia-northeast3`, 동시성·재시도 정책). 환경별로 달라지는 것은 다음 두 가지뿐이다.

- 큐가 속한 Firebase 프로젝트
- 큐가 호출하는 함수 URL (자기 환경의 함수)

환경별로 큐 동시성·재시도 정책을 다르게 두지 않는다. dev 는 부하 테스트의 영향을 prd 에 미치지 않으면서 *실 운영과 같은 멱등성·재시도 거동*을 검증해야 하기 때문이다.

## 9.7 결정적 task ID sanitize/hash 규칙

8장 8.7 이 본 장에 위임한 task ID 규칙을 다음으로 확정한다.

### 9.7.1 논리 키와 실제 task ID 의 분리

논리 키는 8장 정본을 따른다 — `beginSelect-{gameId}-{roundNumber}`, `endRound-{gameId}-{roundNumber}`, `startRound-{gameId}-{roundNumber}`. 그러나 Cloud Tasks 의 task ID 는 다음 두 제약을 가진다.

- task ID 는 길이·문자 집합 제한이 있고, 일부 입력 형식(예: `:` 포함 식별자)은 그대로 사용할 수 없다.
- 결정적 task name 으로 dispatch rate 가 한 prefix 에 몰리면 큐 내부 분포가 비균등해져 throughput 저하가 일어난다.

따라서 실제 task ID 는 논리 키를 그대로 쓰지 않고, 다음 규칙으로 산출한다.

### 9.7.2 sanitize/hash 규칙

| 단계 | 규칙 |
|---|---|
| (i) 논리 키 정규화 | `kind`, `gameId`, `roundNumber` 를 NFC + 소문자화. `gameId` 의 비허용 문자는 `_` 로 치환 |
| (ii) hash prefix 산출 | `sha256(gameId)` 의 앞 8자 hex 를 hash prefix 로 사용. 8자(32bit) 는 8장 8.9 의 샤드 매핑과 같은 근거(JS 안전 정수 안)에서 충분히 균등 |
| (iii) task ID 조합 | `{kind}-{hashPrefix}-{roundNumber}` 형태로 결합. 예: `beginSelect-a1b2c3d4-1` |
| (iv) 길이 검증 | 결과가 Cloud Tasks 의 ID 한계(현재 500자 미만) 를 초과하지 않음을 확인. 본 시스템의 입력 도메인에서는 해당하지 않는다 |
| (v) 재사용 회피 윈도 | 삭제·완료된 task ID 는 일정 시간 재사용되지 않을 수 있으므로, 같은 회차 task 를 삭제 후 즉시 재생성하는 운영 절차는 피한다(8장 8.7 정본 재확인) |

### 9.7.3 멱등성 자연 보장

위 규칙에서 `(kind, gameId, roundNumber)` 가 같으면 task ID 도 결정적으로 같다. 따라서 동일 조합으로 중복 `createTask` 호출이 발생하면 Cloud Tasks 가 `ALREADY_EXISTS` 로 자연 거부한다. 이 거동은 8장 8.10.1 의 페이즈 전환 멱등성 단위 표를 그대로 만족한다.

`hashPrefix` 가 `gameId` 만으로 산출되어 같은 게임의 모든 라운드가 같은 prefix 에 묶이는 점은 의도된 결과다. 라운드별 dispatch 가 시간차로 흩어지므로 prefix 집중에 따른 throughput 저하 위험이 작고, 같은 게임의 task 들을 운영자가 logging 에서 한꺼번에 식별하기 쉬워진다.

## 9.8 비밀·환경 변수 관리

### 9.8.1 종류와 보관 위치

| 분류 | 예시 | 보관 위치 | 클라이언트 노출 가능 여부 |
|---|---|---|---|
| Firebase 클라이언트 config | API key, project ID, auth domain | 빌드 산출물 / 환경 변수 | 가능 (공개 식별자) |
| 함수 region·프로젝트 ID | `asia-northeast3`, project ID | 빌드 산출물 / 환경 변수 | 가능 |
| service account 키 (필요 시) | Tasks Dispatcher 키 등 | Secret Manager 또는 Functions runtime secret | 절대 불가 |
| 외부 API 비밀 | 매체사·결제 SDK 비밀 등 | Secret Manager | 절대 불가 |
| Admin custom claim 발급 토큰 | 관리자 부여용 시크릿 | Secret Manager | 절대 불가 |

### 9.8.2 주입 원칙

- **클라이언트** — 빌드 타임 환경 변수로 주입한다. dev 빌드는 dev Firebase config, prd 빌드는 prd config 를 받는다.
- **함수** — runtime 환경 변수 또는 Secret Manager 참조로 주입한다. 함수 코드는 어떤 비밀도 하드코딩하지 않는다.
- **로컬** — Emulator 사용 시 `.env.local` 같은 비커밋 파일로 받고, 저장소에는 비밀이 없는 `.env.example` 만 포함한다.

비밀이 실수로 커밋되면 즉시 회전한다. 회전 절차와 사고 보고 라인은 작성 예정 10장에서 다룬다.

## 9.9 Firebase Emulator 로컬 개발

Firebase Emulator 는 dev/prd 를 건드리지 않고 도메인 흐름을 검증하기 위한 1차 환경이다. 보안 규칙과 함수 트랜잭션 가드가 운영 환경과 같은 결과를 내야 한다.

### 9.9.1 Emulator 로 검증 가능한 것

| 검증 대상 | Emulator 지원 |
|---|---|
| Firestore 보안 규칙(6장 6.10) | 직접 지원 |
| Callable 함수(`joinGame` / `submitChoice` / `submitWinnerInfo`) | 직접 지원 |
| `waiting → countdown → select → reveal → ended` 페이즈 전환 트랜잭션 가드(8장 8.5) | 직접 지원 |
| Pub/Sub 트리거 함수 `processBatch` | 직접 지원 |
| 익명 Auth 발급 흐름 | 직접 지원 |
| SPA rewrite 와 `firebase.json` headers | hosting emulator 로 직접 지원 |

### 9.9.2 Emulator 가 직접 지원하지 않는 것

Cloud Tasks 는 Firebase Emulator 가 직접 모킹하지 않는다. 본 장은 두 우회 전략을 정본으로 둔다.

| 전략 | 동작 | 사용 시점 |
|---|---|---|
| (i) 인메모리 큐 어댑터 | 코드 안에서 task enqueue 를 인메모리 큐로 바꾸고, schedule time 도달 시 직접 함수 핸들러를 호출. OIDC 검증은 우회 | 단위 테스트, 로컬 통합 테스트 |
| (ii) HTTP 직접 호출 | scheduled time 도달 시점에 Emulator 의 함수 endpoint 를 직접 POST. OIDC 우회를 위한 dev-only 분기를 함수 측에 둔다 | 수동 시나리오 테스트 |

두 우회 모두 *Emulator 한정* 이며, prd 코드에는 OIDC 우회 분기가 절대 들어가서는 안 된다. 우회 분기의 활성화는 환경 식별 변수(9.4.3) 가 dev 또는 emulator 인 경우로 제한한다.

### 9.9.3 검증 절차

로컬 개발자는 다음 흐름을 수행해 dev 배포 전 회귀를 잡는다.

- Emulator 시작 → 보안 규칙 단위 테스트 → Callable 함수 단위 테스트 → `waiting` 입장부터 `ended` 까지 1라운드 시나리오를 끝까지 진행하는 통합 시나리오.
- 보안 규칙 변경 시 6장 정본과의 일치 여부를 Emulator 로 재검증한다.
- 함수 변경 시 8장 8.5 의 페이즈 전이 5종(`waiting → countdown`, `countdown → select`, `select → reveal`, `reveal → countdown`, `reveal → ended`) 이 모두 올바르게 가드되는지 통합 시나리오로 검증한다. `select` 마감 전 `adminChoice` 가 공개 문서에 노출되지 않는지도 함께 확인한다.

부하·1만 동접 검증은 Emulator 의 범위가 아니다 — 부하 테스트는 작성 예정 12장에서 다룬다.

## 9.10 배포 단위와 절차

### 9.10.1 배포 단위

Firebase Hosting / Functions / Firestore rules 는 한 명령으로 함께 배포할 수 있으나, 본 장은 다음 단위로 분리한 배포를 정본으로 한다.

| 단위 | 포함 산출물 | 회전 빈도 |
|---|---|---|
| Hosting | React 빌드 산출물 | 잦음 (UI 수정마다) |
| Functions | 도메인 함수 코드 | 보통 (계약 변경 시) |
| Firestore rules / indexes | 보안 규칙·인덱스 | 드뭄 (정책 변경 시) |
| Cloud Tasks 큐 정의 | 큐 이름·동시성·재시도 | 매우 드뭄 |
| IAM 바인딩 | service account · invoker 권한 | 매우 드뭄 |

빈도 차이가 큰 산출물을 같은 배포 단위에 묶으면 작은 UI 수정에도 보안 규칙이 의도치 않게 함께 갱신될 수 있다. 단위를 분리하면 회귀 영향을 작게 유지할 수 있다.

### 9.10.2 배포 흐름

dev → prd 의 일반 흐름은 다음을 따른다.

- 코드 머지 후 dev 환경에 단위별로 배포한다.
- Emulator·dev 에서 회귀 검증과 1라운드 시나리오를 통과한다.
- prd 배포는 별도 권한을 가진 운영자가 수행한다. 자동화 도구(GitHub Actions 등) 채택 여부는 13장 미결정 큐로 둔다.
- Firestore rules 와 IAM 변경은 prd 배포 전 별도 동료 리뷰를 의무화한다.

### 9.10.3 롤백

| 산출물 | 롤백 방법 |
|---|---|
| Hosting | 이전 채널 release 로 즉시 rollback |
| Functions | 이전 commit 으로 재배포. 트랜잭션 가드가 멱등성을 보장하므로 도중 롤백도 안전(8장 8.10) |
| Firestore rules | 이전 룰 파일로 재배포 |
| Cloud Tasks 큐 / IAM | 변경 명령을 역순으로 재실행. 비활성화 후 재발행 절차는 운영 SOP |

롤백 절차의 운영자 권한과 사고 보고 라인은 작성 예정 10장에서 다룬다.

## 9.11 인앱웹뷰 호환성 메모

본 시스템의 사용자는 일반 브라우저가 아니라 NBT 오퍼월 인앱웹뷰로 진입한다(5장 5.2). 호스팅 측면에서 이 진입 컨텍스트가 강제하는 제약이 있다.

| 제약 | 호스팅 측 대응 |
|---|---|
| 인앱웹뷰는 일회성 진입이 잦음 | `index.html` 을 캐시하지 않거나 짧은 TTL 로 두어 매 진입마다 최신 진입점을 받는다(9.3.2) |
| 인앱웹뷰의 쿠키·storage 정책이 일반 브라우저와 다를 수 있음 | Firebase Anonymous Auth 의 토큰 저장은 5장 5.4 정본대로 동작한다고 본다. 쿠키 의존 분기는 도입하지 않는다 |
| 인앱웹뷰의 URL 보존 동작이 단말·OS 별로 다름 | URL 쿼리 파라미터 5종은 클라이언트 진입 시 즉시 페이로드로 추출해 `joinGame` 호출에 담는다(5장 5.5). 호스팅 단계에서 파라미터를 가공하지 않는다 |
| 네이티브 네비게이션바와의 시각적 충돌 | 이는 호스팅이 아니라 UI 레이아웃 결정이다. 본 장은 다루지 않는다 |

인앱웹뷰의 단말별 호환성 검증과 부하 테스트 관계는 작성 예정 12장에서 다룬다.

## 9.12 환경별 관측·로그 분리

### 9.12.1 라벨 분리 원칙

dev 와 prd 의 Cloud Logging·Cloud Monitoring 출력은 다음 라벨을 모두 가져야 한다.

- 환경 식별(`env=dev | prd`)
- 함수 이름(`function`)
- 게임 ID(`gameId`)
- 라운드 번호(`roundNumber`)
- batch index (해당 시)

라벨이 누락되면 8장 8.10.4 의 운영 진단 1차 신호가 환경 간에 섞여 stale lease 인지 cross-env 호출 사고인지 구분하기 어려워진다.

### 9.12.2 알림 라우팅

| 신호 | 알림 라우팅 |
|---|---|
| dev 의 함수 5xx 급증 | dev 채널만 |
| prd 의 함수 5xx 급증 | prd 알림 채널 + 운영자 호출 라인 |
| dev 의 batch failed | dev 채널만 |
| prd 의 batch failed | prd 알림 채널 + 운영자 호출 라인 |

알림 채널 구체값과 호출 라인은 작성 예정 10장 운영 정책 및 관리자 업무에서 다룬다.

### 9.12.3 모니터링 대시보드

라운드 진행 상태(`processedBatchCount` / `expectedBatchCount`), 큐 길이, 함수 latency, Firestore read/write 카운트는 환경별로 분리된 대시보드를 둔다. 운영 단계에서는 minInstances 활성화 시점·종료 시점도 같은 대시보드에서 관찰한다(8장 8.11 의 *시점* 정본 참고).

## 9.13 확정 사항과 미결정 사항

### 확정 (9장 정본)

- 호스팅은 Firebase Hosting 채택. region 은 `asia-northeast3` 고정.
- `index.html` 은 no-cache 또는 짧은 TTL, 해시 정적 자산은 immutable. 해시 없는 자산은 짧은 TTL 또는 ETag 재검증.
- SPA rewrite 는 모든 경로를 `/index.html` 로 매핑.
- 환경 4축 격리 — Firebase 프로젝트 / Cloud Tasks 큐 / service account / 함수 URL 모두 환경별 분리.
- 환경 식별은 명시적 환경 변수 한 가지(`ENV=dev | prd`) 로만 분기.
- 함수 측 OIDC 검증은 `serviceAccountEmail` 과 `audience` 두 축을 모두 매칭. 검증 실패 시 401, 가드 불일치 시 200 + no-op.
- Cloud Tasks 큐 동시성·재시도 정책은 환경 무관 동일. 환경별로 달라지는 것은 프로젝트와 함수 URL 뿐.
- 결정적 task ID 산출 규칙 — `{kind}-{sha256(gameId).slice(0,8)}-{roundNumber}`. 같은 조합 중복 createTask 시 `ALREADY_EXISTS` 로 자연 거부.
- 비밀은 Secret Manager 또는 Functions runtime secret 로만 주입. 코드 하드코딩 금지.
- Firebase Emulator 가 Cloud Tasks 를 직접 모킹하지 않는 점은 인메모리 큐 어댑터 또는 HTTP 직접 호출로 우회. 우회 분기는 dev/emulator 한정으로 격리.
- 배포 단위는 Hosting / Functions / Firestore rules·indexes / Cloud Tasks 큐 / IAM 다섯으로 분리. prd 배포의 rules·IAM 변경은 동료 리뷰 의무.
- 환경 식별 라벨(`env=dev | prd`) 을 모든 로그·메트릭에 부여. 알림 채널 분리.

### 미결정 (모두 13장 위임 또는 11/12 의존)

| 항목 | 결정 필요 내용 |
|---|---|
| dev/prd 환경 분리 최종 채택 | 옵션 (a) prd 단독 / (b) 두 프로젝트 / (c) 단일 프로젝트 환경 변수 분기 — 본 장은 (b) 권장 |
| `index.html` 캐시 TTL 구체값 | 0초 / 60초 / 300초 등 |
| Custom domain 도입 여부 | Firebase Hosting 기본 도메인 vs 별도 도메인 |
| CI/CD 자동화 도구 채택 | GitHub Actions 등 자동화 도입 시점과 범위 |
| `cleanUrls` / `trailingSlash` | SPA 라우팅 정책 확정 시 |
| `minInstances` 활성화 자동화 | 행사 시작 30분 전 활성화·종료 직후 비활성화의 자동화 여부. 시점 정본은 8장 8.11, 구체값은 11장 |
| BigQuery Export | 어뷰징 사후 검증·운영 분석 export 여부(2장 2.4 와 정합) |
| App Check | reCAPTCHA v3 등 봇 차단 도입 여부(2장 2.4 와 정합) |
