# 8. 자동진행 및 서버리스 함수

> 가위바위보 챌린지가 라운드 페이즈를 어떻게 자동으로 진행하고, 서버 함수들이 어떤 계약과 멱등성 위에서 동작하는지를 정의한다.
>
> - **다루는 것** — 자동 진행 메커니즘 선택과 단계 전략, 함수 인벤토리, 페이즈 전환 트랜잭션 정본, 함수별 계약 상세, Cloud Tasks 큐 설계, Pub/Sub batch manifest, 샤드 매핑 함수 정본, 멱등성·재시도·관측, 콜드 스타트 원칙
> - **위임하는 것** — 컬렉션·필드 정의와 보안 규칙 코드, 동시성·정원·재진입 정책, 호스팅·환경 분리, 비용 수치, 운영자 업무, 미결정 정책 (각 전담 챕터로)
> - **상위 문서** — 페이즈 흐름은 [3. 게임 룰 및 라운드 흐름](./03_게임_룰_및_라운드_흐름.md), 단일 쓰기 게이트웨이는 [4. 시스템 아키텍처](./04_시스템_아키텍처.md), 데이터 모델 정본은 [6. 데이터 모델 및 보안 정책](./06_데이터_모델_및_보안_정책.md), 동시성·정원·중복참여 정책은 [7. 동시성·정원·중복참여 정책](./07_동시성_정원_중복참여_정책.md) 을 따른다

## 8.1 이 문서의 역할

- **목적** — 다른 챕터들이 위임한 "메커니즘·계약 수준" 정의를 한 곳에 고정한다. 무엇이 일어나는가(룰)는 3장, 어떤 데이터에 영향을 주는가는 6장, 왜 그 분기인가(정책)는 7장이 정의했다. 본 장은 그 위에서 **어떻게 atomic·멱등하게 실행되는가**(구현 계약) 만 다룬다.
- **범위** — 함수 인벤토리, 페이즈 전환 트랜잭션 정본, 함수별 계약, Cloud Tasks/Pub/Sub 설계, 샤드 매핑 함수 확정, 멱등성·재시도 단위. SDK 호출 코드와 트랜잭션 의사코드는 본 장의 범위가 아니다.
- **위임 대상**

## 8.2 설계 원칙

본 장의 모든 결정은 다음 다섯 원칙 위에서 성립한다. 원칙은 추상적 선언이 아니라 8.5 ~ 8.10 의 구체 결정이 환원되는 근거다.

- **결정적 멱등성** — 모든 페이즈 전이와 배치 처리는 트랜잭션 가드와 결정적 식별자(task name, batch index) 위에서 동작한다. 재시도가 들어와도 같은 결과를 만들거나 즉시 ack 한다.
- **단일 진입점 분리** — 클라이언트 호출이 가능한 표면(Callable)과 내부 트리거 표면(Cloud Tasks HTTP / Pub/Sub) 을 분리한다. 보안 규칙은 클라이언트 직접 쓰기를 차단하는 방어선만 담당한다.
- **사전 고정** — 처리 도중 외부 상태가 변해도 결과가 흔들리지 않도록, `endRound` 시점에 batch UID range 와 `adminChoice` 를 즉시 동결한다.
- **서버 시간 신뢰** — 모든 마감 검증은 `Timestamp.now()` 서버 시간만 사용한다. 클라이언트가 보낸 시각·라운드 번호는 입력일 뿐 신뢰하지 않는다.
- **상태 머신 = 트랜잭션 가드 입력** — `phase`, `currentRound`, `players.status`, `batches.status` 는 곧 트랜잭션 가드의 입력이다. 매 트랜잭션은 자기 가드 조건을 명시하고, 가드 불일치 시 no-op 으로 빠진다.

## 8.3 자동 진행 메커니즘 선택과 단계 전략

라운드 페이즈는 시각이 도달하면 자동으로 다음 페이즈로 전이되어야 한다. 본 장은 운영 단계에서 **Cloud Tasks** 를 채택하고, 검증 단계에 한해 **클라이언트 트리거 + 결정적 task name 멱등 가드** 를 보조 수단으로 허용한다.

### 8.3.1 메커니즘 비교

| 옵션 | 동작 | 장점 | 한계 |
|---|---|---|---|
| **Cloud Tasks (채택)** | 함수가 다음 페이즈 호출을 큐에 결정적 task name 으로 예약, 시각 도달 시 큐가 함수 자동 호출 | 정확한 timing, 자연 멱등(`ALREADY_EXISTS`), 라운드 시간 가변 가능, 자동 재시도 | 큐 권한·OIDC 셋업 필요 |
| Cloud Scheduler | Cron 식 정기 호출 등록 | 단순 | 라운드 시간 가변 불가, 분 단위 정밀도 한계 → 3장의 "라운드 N분마다 자동 진행"·초 단위 카운트다운 요건 미충족 |
| 클라이언트 트리거 단독 | 시각 도달 시 클라이언트가 다음 페이즈 함수 호출 | 인프라 0 | 1만 동시 호출 비용, 4장의 "클라이언트 신뢰 금지" 원칙과 충돌 |
| 함수 내부 `setTimeout` | 함수 실행 중 setTimeout 으로 다음 페이즈 트리거 | 인프라 0 | 함수 응답 후 종료 → 타이머 실행 보장 ✕, 라운드 누락 위험 |

Cloud Scheduler·setTimeout·클라이언트 단독은 **신뢰성 기준(라운드 누락 0건)** 을 충족하지 못하므로 운영 단계 채택에서 탈락한다.

### 8.3.2 단계 전략 (검증 → 운영)

검증 단계에서는 큐 권한·OIDC 인증 셋업 부담을 운영 단계로 미루기 위해 다음 분기를 허용한다.

- **검증 단계** — 클라이언트가 카운트다운 종료 시 `startRound` 계열 Callable 변형(`beginSelect` 역할) 을, `roundEndsAt` 시각 도달 시 `endRound` Callable 변형을 호출한다. 함수는 운영 단계와 같은 서버 시간 가드(8.5) 로 멱등성을 유지하므로 다중 클라이언트가 동시에 호출해도 한 번만 실제 처리가 일어난다.
- **운영 단계** — `startRound` 가 Cloud Tasks 에 결정적 task name 으로 `beginSelect` 를 예약하고, `beginSelect` 가 `endRound` 를 예약한다. 클라이언트는 자동 진행에 관여하지 않는다.

함수 코드는 환경 변수 한 줄 분기로 양쪽 모드를 모두 지원한다. 단, **트랜잭션 가드는 두 모드에서 같다** — 즉 검증 단계 코드에서 운영 단계로 옮겨갈 때 동시성·멱등성 동작이 동일하게 유지된다.

## 8.4 함수 인벤토리

본 장의 모든 함수는 4장 4.5 의 단일 쓰기 게이트웨이 표를 구체화한다. Callable 표면은 클라이언트가 직접 호출할 수 있고, 내부 트리거 표면은 Cloud Tasks 또는 Pub/Sub 만이 호출한다. `beginSelect` 는 별도 클라이언트 API 가 아니라 `startRound` 계열의 Cloud Tasks step 으로, `countdown → select` 전이만 담당한다.

### 8.4.1 Callable 함수

| 함수 | 호출 주체 | 책임 |
|---|---|---|
| `joinGame` | 클라이언트 | URL 파라미터 5종 정규화·검증, 본인 재호출 idempotent 복원, `adisonUid` 중복 차단, 신규 입장 정원 검증, `aliveShardIndex` 저장과 카운터 갱신 (단일 트랜잭션) |
| `submitChoice` | 클라이언트 | 본인·생존·현재 라운드·마감 전 여부 검증 후 본인 선택 필드 갱신 |
| `submitWinnerInfo` | 우승자 클라이언트 | 우승자 본인 여부와 1회 제출 검증 후 비공개 수령 정보 저장 |

### 8.4.2 내부 트리거 함수

| 함수 | 호출 주체 | 책임 |
|---|---|---|
| `startRound` | 운영자/내부 (또는 마지막 batch 의 결정적 enqueue) | `waiting/reveal → countdown` 전이, 라운드 번호·라운드 문서 생성, Cloud Tasks 에 `beginSelect` 예약 |
| `beginSelect` | Cloud Tasks HTTP (`startRound` 계열 step) | `countdown → select` 전이, `roundEndsAt`/`rounds/{n}.endsAt` 설정, Cloud Tasks 에 `endRound` 예약 |
| `endRound` | Cloud Tasks HTTP | `phase = reveal` 전이와 `adminChoice` 결정을 멱등 트랜잭션으로 처리한 뒤 batch manifest 동결 후 Pub/Sub 분산 dispatch |
| `processBatch` | Pub/Sub | 1000명 단위로 승패 판정, 탈락 처리, 입장 시 샤드 기준 카운터 차감, 라운드 집계 부분 합산, batch 멱등성 기록 |

## 8.5 페이즈 전환 트랜잭션 정본

페이즈 전이는 모두 트랜잭션 가드 안에서 처리한다. 본 절은 5개 전이를 enumeration 으로 고정하고, 각 전이가 같은 트랜잭션 안에서 갱신할 필드와 트랜잭션 외부의 부수 효과를 정의한다.

5개 전이를 모두 다룬다.

1. `waiting → countdown` (첫 라운드 시작)
2. `countdown → select`
3. `select → reveal`
4. `reveal → countdown` (다음 라운드)
5. `reveal → ended` (우승 또는 이월)

| # | 전이 | 트리거 | 가드 조건 | 같은 트랜잭션에서 갱신할 필드 | 외부 효과 |
|---|---|---|---|---|---|
| 1 | `waiting → countdown` | `startRound` (Admin/내부) | `phase == "waiting"` AND (`now() >= closesAt` 또는 운영자 강제 시작 신호) | `phase = "countdown"`, `currentRound = 1`, `rounds/1` create(`phase = "countdown"`, `startedAt`, `selectStartsAt`), 첫 라운드 시작 직전 `totalPlayers` 고정 | Cloud Tasks 에 `beginSelect-{gameId}-1` 예약(`schedule_time = rounds/1.selectStartsAt`). `aliveCount` 보정은 8.5.2 시점 계약을 따름 |
| 2 | `countdown → select` | Cloud Tasks `beginSelect` (`startRound` 계열 step) | `phase == "countdown"` AND `currentRound == n` AND `now() >= rounds/{n}.selectStartsAt` | `phase = "select"`, `rounds/{n}.phase = "select"`, `roundEndsAt`(select 마감), `rounds/{n}.endsAt` | Cloud Tasks 에 `endRound-{gameId}-{n}` 예약 |
| 3 | `select → reveal` | Cloud Tasks `endRound` HTTP | `currentRound == roundNumber` AND ((`phase == "select"` AND `now() >= roundEndsAt`) OR (`phase == "reveal"` AND (`manifestStatus != "ready"` OR `processedBatchCount < expectedBatchCount`))) | 첫 진입에서만 `phase = "reveal"`, `rounds/{n}.phase = "reveal"`, `rounds/{n}.adminChoice`(서버 무작위), `rounds/{n}.revealedAt`, `rounds/{n}.survivorsBefore`, `rounds/{n}.manifestStatus = "building"`, `rounds/{n}.expectedBatchCount = 0`, `rounds/{n}.processedBatchCount = 0` | 트랜잭션 커밋 후 batch manifest 영속화 → persisted batch 문서 기준 Pub/Sub `process-batch` publish |
| 4 | `reveal → countdown` | batch 완료 finalizer 가 결정적 task `startRound-{gameId}-{n+1}` enqueue | `processedBatchCount == expectedBatchCount` AND `survivorsAfter >= 2` | `phase = "countdown"`, `currentRound = n+1`, `rounds/{n+1}` create(`phase = "countdown"`, `startedAt`, `selectStartsAt`) | Cloud Tasks 에 `beginSelect-{gameId}-{n+1}` 예약(`schedule_time = rounds/{n+1}.selectStartsAt`). `aliveCount` 보정은 8.5.2 시점 계약을 따름 |
| 5 | `reveal → ended` | batch 완료 finalizer | `processedBatchCount == expectedBatchCount` AND (`survivorsAfter == 1` 또는 `survivorsAfter == 0`) | `phase = "ended"`, `endedReason`(`winner` 또는 `carryover`), `winnerNickname`(우승 시), `finishedAt`, 우승 시 `result/summary` create | `aliveCount` 보정은 8.5.2 시점 계약을 따름 |

### 8.5.1 가드 확장 근거 (전이 #3)

전이 #3 의 가드는 단순 `phase == "select"` 가 아니라 **첫 진입**과 **복구 진입** 두 분기를 가진다. 첫 진입은 반드시 `now() >= roundEndsAt` 를 만족해야 하므로 검증 단계의 클라이언트 Callable 변형도 라운드를 조기 종료할 수 없다. 복구 진입은 이미 `phase == "reveal"` 인 상태에서 manifest 생성·publish 가 완료되지 않았거나 batch 처리가 끝나지 않은 경우만 허용한다.

복구 진입에서는 `adminChoice` 를 다시 뽑지 않는다. 첫 진입 때 저장된 `rounds/{n}.adminChoice` 와 `revealedAt` 을 그대로 유지하고, persisted batch manifest 를 기준으로 누락 publish 만 복구한다. 이 패턴이 8.10 의 결정적 멱등성과 함께 partial publish 장애를 흡수한다.

### 8.5.2 `aliveCount` 보정 시점

`aliveCount` 공개 캐시는 7장 7.6 정본에 따라 라운드 경계에서 보정한다. 8장은 **시점** 을 정본으로 고정하고, 보정 주체는 13장 미결정 큐로 유지한다.

- **첫 라운드 시작 직전** — 전이 #1 경계에서 10개 샤드를 합산해 `games.aliveCount` 를 보정하고, `games.totalPlayers` 를 최종 참가자 수로 한 번 고정한다.
- **각 라운드 종료 직후** — 모든 batch 가 완료된 시점, 즉 전이 #4 또는 #5 의 가드 검증 직전에 10개 샤드를 합산해 `games.aliveCount` 를 보정한다. 이 값은 다음 라운드 `countdown` 진입 시 그대로 사용한다.
- **다음 라운드 시작 직전** — 전이 #4 자체에서는 별도 합산을 반복하지 않는다. 직전 라운드 종료 보정값을 사용하고, `games.totalPlayers` 는 변경하지 않는다.

보정의 *주체* — 즉 합산 호출이 페이즈 전환 함수 내부에 직접 들어가는지, 별도 주기적 집계 함수가 담당하는지 — 는 13장 미결정 큐로 둔다. 본 장은 중복 합산을 피하기 위해 실행 시점을 첫 라운드 시작 직전과 각 라운드 종료 직후로 좁힌다.

## 8.6 함수별 계약 상세

본 절은 각 함수의 입력·인증·트랜잭션 단계·외부 효과·실패 응답 코드를 정의한다. SDK 시그니처와 의사코드는 본 장 범위가 아니다.

### 8.6.1 `joinGame` (Callable)

| 항목 | 계약 |

### 8.6.4 `endRound` (Cloud Tasks HTTP)

| 항목 | 계약 |
|---|---|
| 호출 주체 | Cloud Tasks (운영) 또는 클라이언트 Callable 변형(검증 단계만) |
| 인증 | Cloud Tasks OIDC 토큰의 `serviceAccountEmail` 과 `audience` 매칭 검증. 검증 단계 변형은 Callable `request.auth.uid` 만 필요 |
| 트랜잭션 단계 | 8.5 의 전이 #3 정본을 따름. 첫 진입은 `phase == "select"` AND `now() >= roundEndsAt` 를 반드시 만족해야 한다. 첫 진입에서만 `adminChoice` 를 `crypto.randomInt(0, 3)` 으로 결정하고, 재시도 분기에서는 기존 `adminChoice` 를 유지한다 |
| 외부 효과 (트랜잭션 외부) | (i) `manifestStatus != "ready"` 이면 현재 생존자(`status == "alive"` AND `lastProcessedRound < n`)의 UID range 를 `__name__` 정렬로 cursor 분할하고 deterministic `batches/{i}` 문서(`status = "pending"`, range, limit)를 idempotent upsert 한다, (ii) 기존 batch 문서가 있으면 range/limit 이 같은지 검증하고 불일치 시 `manifestStatus = "failed"` 와 진단 메시지를 기록한 뒤 운영자 개입 대상으로 둔다, (iii) 모든 batch 문서가 일관되게 기록된 뒤 `rounds/{n}.expectedBatchCount` 와 `manifestStatus = "ready"` 를 set, (iv) persisted batch 문서를 기준으로 Pub/Sub `process-batch` 토픽에 publish. `manifestStatus == "ready"` 인 재시도는 manifest 를 재산출하지 않고 기존 batch 문서만 재발행/복구한다 |
| 멱등성 | 결정적 task name `endRound-{gameId}-{n}` 으로 자연 멱등. 또한 persisted manifest 와 가드 두 분기로 partial publish 후 재시도가 누락 publish 만 복구한다 |
| 실패 응답 | OIDC 검증 실패 시 401, 가드 불일치 시 200 + no-op |

### 8.6.5 `processBatch` (Pub/Sub)

| 항목 | 계약 |
|---|---|
| 호출 주체 | Pub/Sub `process-batch` 토픽 메시지 |
| 메시지 페이로드 | `{ gameId, roundNumber, batchIndex, expectedBatchCount, startAfterUid, endAtUid, limit }` |
| 단계 | (i) `batches/{i}` 를 트랜잭션으로 claim 한다. `done` 이면 즉시 ack, `processing` 이고 `startedAt` 이 stale lease 기준 전이면 재claim, stale 이 아니면 ack 하지 않고 재시도를 기다린다, (ii) persisted UID range 를 `__name__` cursor 로 조회하고 서버에서 대상 후보를 필터링한다. 후보는 `status == "alive"` 이거나 이미 이번 라운드에서 처리된 `lastProcessedRound == n` / `eliminatedRound == n` 플레이어이며, 이전 라운드 탈락자는 제외한다, (iii) 아직 `lastProcessedRound < n` 인 생존자만 새로 판정한다. `choiceRound == n` 인 선택만 유효 선택으로 보고, 그 외는 미제출자로 판정한다, (iv) 애디슨에게 이긴 사용자는 생존으로 유지하고, 비긴 사용자·패자·미제출자는 `eliminated` 로 갱신하면서 `lastProcessedRound = n` set 한다. 생존자도 `lastProcessedRound = n` set 한다, (v) 실제로 이번 시도에서 alive→eliminated 전이된 사용자만 `aliveShardIndex` 로 그룹핑해 샤드별 `count -N` 차감, (vi) 모든 player write 가 성공한 뒤 persisted UID range 를 Firestore 에서 재조회해 batch 최종 집계를 계산한다. 같은 함수 attempt 안의 in-memory buffer 는 최적화로만 사용할 수 있고 crash/retry 후 정본으로 삼지 않는다, (vii) `batches/{i}.status = "done"` 으로 전환하는 단 한 번의 트랜잭션에서 batch 집계값을 `rounds/{n}` 에 increment 하고 `rounds/{n}.processedBatchCount += 1` 을 반영한다 |
| 트랜잭션 경계 | **1000명 갱신을 단일 Firestore 트랜잭션에 묶지 않는다.** Firestore 트랜잭션 시간 한도와 batch/write 한계와 충돌하기 때문이다. 대신 persisted UID range 를 여러 chunk 로 나누고, 각 chunk 트랜잭션 안에서 `lastProcessedRound < n` 인 player 전이와 해당 `aliveShardIndex` 샤드 차감을 함께 반영한다. 구현은 chunked transaction, BulkWriter, 또는 서버 병렬 write 중 하나를 선택할 수 있지만, player 전이와 해당 샤드 차감의 멱등성은 반드시 유지한다. batch 전체 집계와 `processedBatchCount += 1` 은 모든 chunk 성공 후 `batches/{i}.status` 를 `done` 으로 바꾸는 단 한 번의 트랜잭션에서만 반영한다. 부분 실패는 두 단계 가드로 흡수한다 — `batches/{i}.status` + `startedAt` lease 가 디스패치/claim 멱등성을 보장하고, 각 `players/{userId}.lastProcessedRound` 가 player 단위 side effect 멱등성을 보장한다. 같은 batch 가 두 번 도착해도 `done` 이면 즉시 ack 하고, `processing` 에서 crash 한 batch 는 lease 만료 후 재claim 한다. |
| 외부 효과 | `processedBatchCount` 증가 결과가 `expectedBatchCount` 에 도달한 처리자가 batch 완료 finalizer 를 시도한다. 생존자 수가 2명 이상이면 결정적 task name `startRound-{gameId}-{n+1}` 을 enqueue 하고, 0~1명이면 `reveal → ended` 처리를 수행한다 |
| 멱등성 단위 | `(roundNumber, batchIndex)` (7.5 정합) |

## 8.7 Cloud Tasks 큐 설계

운영 단계 자동 진행은 단일 큐 `game-rounds` 위에서 동작한다. 큐 설정은 멱등성·재시도·동시성·인증 네 축으로 정해진다.

| 항목 | 값 / 정책 |
|---|---|
| 큐 이름 | `game-rounds` |
| 위치 | `asia-northeast3` (Hosting/Functions 와 동일 region) |
| 동시성 | `max-dispatches-per-second = 10`, `max-concurrent-dispatches = 5` (라운드당 task 수가 적어 보수적 설정으로 충분) |
| 재시도 | `max-retry-duration = 300s`, `min-backoff = 1s` (지수 backoff). Cloud Tasks 가 자체 재시도 |
| 결정적 task name | 논리 키는 `beginSelect-{gameId}-{roundNumber}`, `endRound-{gameId}-{roundNumber}`, `startRound-{gameId}-{roundNumber}` 이지만 실제 Cloud Tasks task ID 는 `kind-{hash(gameId)}-{roundNumber}` 처럼 균등 분포 hash prefix 를 사용한다. 동일 조합으로 중복 `createTask` 호출 시 `ALREADY_EXISTS` 로 자연 거부한다. 삭제·완료된 task ID 는 일정 시간 재사용되지 않을 수 있으므로 같은 회차 task 를 삭제 후 즉시 재생성하는 운영 절차는 피한다. 세부 sanitize/hash 규칙은 9장에서 확정한다 |

## 8.8 Pub/Sub 분산 처리와 batch manifest

라운드 종료 시 1만 명을 단일 함수에서 처리하지 않고 Pub/Sub 으로 1000명 단위 배치로 분산 dispatch 한다.

### 8.8.1 토픽

- 토픽: `process-batch`
- 구독자: `processBatch` 함수 (Pub/Sub 트리거)
- 재시도: Pub/Sub 자체 재시도 + dead-letter 토픽 옵션 (운영 단계에서 활성화)

### 8.8.2 메시지 페이로드 스키마

```text
{
  gameId:             string,
  roundNumber:        number,
  batchIndex:         number,
  expectedBatchCount: number,
  startAfterUid:      string | null,
  endAtUid:           string | null,
  limit:              number
}
```

### 8.8.3 batch manifest 사전 고정 알고리즘

batch 분할은 처리 도중 상태 변경으로 결과가 흔들리지 않도록 **`endRound` 함수 안에서 한 번에 동결**된다.

1. `endRound` 트랜잭션이 `phase = "reveal"` 로 전이하고 commit 된다. 이때 `manifestStatus = "building"`, `expectedBatchCount = 0`, `processedBatchCount = 0` 으로 초기화한다.
2. 같은 함수 안에서 `players` 컬렉션을 `__name__` 정렬로 cursor scan 하면서 처리 대상(`status == "alive"` AND `lastProcessedRound < n`) 의 UID range 를 분할한다. batch 크기는 1000명 기본.
3. 분할 결과를 deterministic path 인 `games/{gameId}/rounds/{n}/batches/{i}` 문서로 영속화한다. 각 batch 문서는 `batchIndex`, `status = "pending"`, `startAfterUid`, `endAtUid`, `limit` 을 가진다. 재시도 중 기존 batch 문서가 있으면 range/limit 일치 여부를 검증하고, 일치하면 idempotent 성공으로 본다.
4. 기존 batch 문서와 새 분할 결과가 충돌하면 `manifestStatus = "failed"` 와 진단 메시지를 기록하고 publish 를 중단한다. 운영자 복구 절차는 10장으로 위임한다.
5. 모든 batch 문서가 일관되게 기록된 뒤에만 `rounds/{n}.expectedBatchCount` 를 최종 batch 수로 set 하고 `manifestStatus = "ready"` 로 전환한다.
6. Pub/Sub publish 는 새로 scan 한 range 가 아니라 persisted batch 문서들을 기준으로 수행한다.

cursor scan 도중 새 입장이 들어오는 시나리오는 발생하지 않는다 — 7장 7.3.4 에 따라 입장 게이트는 `countdown` 진입 시점에 이미 닫혀 있기 때문이다. 따라서 manifest 동결은 입장 흐름과 경합하지 않는다.

### 8.8.4 partial publish 복구

publish 가 4/10 에서 함수 crash 등으로 중단되면 batch 4~9 는 영원히 처리되지 않을 수 있다. 본 장은 8.5 의 전이 #3 가드와 persisted manifest 로 이를 흡수한다.

- Cloud Tasks 가 `endRound-{gameId}-{n}` 를 재시도하면 함수가 다시 진입한다.
- 첫 분기(`phase == "select"`) 는 이미 거짓이다.
- 두번째 분기(`phase == "reveal" AND (manifestStatus != "ready" OR processedBatchCount < expectedBatchCount)`) 가 참이면 복구 단계로 들어간다.
- `manifestStatus != "ready"` 이면 아직 publish 가능한 완성 manifest 가 없다는 뜻이므로 batch 문서를 완성한 뒤 `expectedBatchCount` 를 set 하고 `manifestStatus = "ready"` 로 전환한다. 기존 partial batch 문서와 새 분할 결과가 불일치하면 `manifestStatus = "failed"` 로 고정하고 Pub/Sub publish 를 하지 않는다.
- `manifestStatus == "ready"` 이면 manifest 를 다시 산출하지 않고 이미 영속화된 `batches/{i}` 문서를 읽어 `pending`, `failed`, 또는 stale `processing` batch 만 재발행한다. `done` batch 는 재발행하지 않는다.

이 패턴은 batch index 와 UID range 의 대응을 재시도 사이에서도 불변으로 유지해, 일부 batch 가 처리된 뒤 manifest 를 재산출하면서 누락자가 생기는 문제를 막는다.

## 8.9 샤드 매핑 함수 정본

7장 7.3.2 가 본 장에 위임한 샤드 매핑 함수를 다음으로 확정한다.

```text
shardIndex = parseInt(adisonUidHash.slice(0, 8), 16) % 10
```

### 8.9.1 근거

- `adisonUidHash` 는 `sha256(normalize(adisonUid))` 결과로 64자 hex(256bit) 다(6장 6.6 및 6.8.6 정본).
- 64자 전체를 한 번에 정수로 변환하면 JavaScript 의 안전 정수 한도(`2^53`) 를 넘어 정밀도 손실이 발생한다.
- 앞 8자 hex(32bit) 만 취하면 `2^32` 범위 안에 있어 `parseInt(_, 16)` 이 정확하다. 이 범위는 mod 10 분포를 균등하게 만들기에 충분히 크다.
- 같은 사용자의 어떤 호출에서도 `adisonUidHash` 가 동일하므로 매핑은 결정적이다 — 7.3.3 의 입장-탈락 샤드 대칭성 원칙이 자연 만족된다.

### 8.9.2 사용 위치

- `joinGame` 트랜잭션의 `counters/alive_{shardIndex}` `+1` (입장 시)
- `joinGame` 은 산출한 `shardIndex` 를 `players/{userId}.aliveShardIndex` 에 저장한다
- `processBatch` 의 탈락자 그룹핑 — 탈락자 명단을 입장 시 저장된 `aliveShardIndex` 별로 모아 샤드별 `count -N` 한 번씩 (라운드 종료 시). 탈락 시점에 `adisonUidHash` 로 재계산하지 않는다

## 8.10 멱등성·재시도·관측

### 8.10.1 멱등성 단위

| 작업 | 멱등성 단위 | 메커니즘 |
|---|---|---|
| Cloud Tasks 페이즈 전환 | `beginSelect-{gameId}-{n}`, `endRound-{gameId}-{n}`, `startRound-{gameId}-{n}` | 결정적 task name → `ALREADY_EXISTS` |
| Pub/Sub 배치 처리 | `(roundNumber, batchIndex)` | `batches/{i}.status` + `startedAt` lease 디스패치/claim 가드 |
| Player 갱신 | `userId` × `roundNumber` | `players/{userId}.lastProcessedRound` |
| 페이즈 전이 | `(phase, currentRound)` 조합 | 트랜잭션 가드 (8.5) |

### 8.10.2 재시도 정책

- Cloud Tasks: `max-retry-duration = 300s`, 지수 backoff. 함수가 5xx 또는 timeout 응답하면 재시도.
- Pub/Sub: 자체 재시도 + dead-letter 옵션. `processBatch` 가 처리 실패 시 `batches/{i}.status = "failed"` + `errorMessage` 에 진단 메시지 기록 후 ack 하지 않으면 Pub/Sub 가 재발사한다.
- 재시도 한도 도달 시: `failed` 로 고정한 batch 는 운영자 수동 재실행 또는 알림 대상이 된다 — 운영 절차는 10장 위임.

### 8.10.3 Pre-Mortem 시나리오

1. **부분 publish 후 endRound 재시도** — endRound 트랜잭션은 commit 됐고 publish 가 batch 4/10 에서 함수 crash. → 8.5 전이 #3 의 두번째 분기 가드 + persisted manifest 로 누락 publish 만 재발행. manifest 는 재산출하지 않는다.
2. **processing 상태에서 processBatch crash** — batch 가 `processing` 으로 claim 된 뒤 함수가 종료. → `startedAt` 기반 stale lease 만료 후 같은 batch 를 재claim 한다. 이미 반영된 player 는 `lastProcessedRound` 가드로 중복 처리하지 않고, batch 집계는 persisted UID range 재조회로 재구성한다.
3. **마지막 완료 batch 동시 도착(재시도)** — 두 인스턴스가 처리 완료 직후 다음 라운드 예약을 시도. → `processedBatchCount` 증가 가드와 결정적 task name `startRound-{gameId}-{n+1}` 으로 한 번만 enqueue 됨.
4. **콜드 스타트로 endRound 30초 지연** — 첫 라운드 endRound task 가 발사됐는데 함수가 아직 워밍업 중. → 8.11 의 minInstances 사전 활성화로 콜드 스타트 회피. Cloud Tasks 자동 재시도로도 흡수 가능.

### 8.10.4 관측

- `batches/{i}` 4-state(`pending → processing → done` / `failed`) 와 `errorMessage` 가 운영 진단의 1차 신호다.
- Cloud Logging 에 함수별 trace, Cloud Tasks 에 task 상태/재시도 횟수가 기록된다.
- 라운드별 처리 진행도는 `rounds/{n}.processedBatchCount` / `expectedBatchCount` 비율로 확인한다.

## 8.11 콜드 스타트 원칙

`endRound`, `processBatch`, `startRound` 같은 라운드 트리거 함수의 콜드 스타트가 라운드 마감 시점에 발생하면 처리가 수십 초 지연될 수 있다. 본 장은 다음 원칙만 명시한다.

- 행사 시작 전 일정 시간 동안 라운드 트리거 함수에 `minInstances` 를 활성화해 콜드 스타트를 회피한다.
- 활성화 시점은 행사 시작 30분 전을 기준선으로 잡는다 (워밍업 안전 마진).
- 활성화 종료는 행사 종료 직후로 한다 (불필요한 인스턴스 비용 회피).

`minInstances` 의 **구체 값(인스턴스 수)** 과 **시간당 비용 시뮬레이션**, 그리고 시나리오별 비용 영향은 본 장이 아니라 11장 비용 추정에서 다룬다. 운영자가 실제로 활성화·비활성화를 어떻게 수행하는가(절차, 권한) 는 10장 운영 정책 및 관리자 업무에서 다룬다.

## 8.12 확정 사항과 미결정 사항

### 확정 (8장 정본)

- 자동 진행은 Cloud Tasks 채택, 검증 단계만 클라이언트 트리거 + 결정적 task name 멱등 가드 허용.
- 결정적 task 논리 키: `beginSelect-{gameId}-{n}`, `endRound-{gameId}-{n}`, `startRound-{gameId}-{n}`. 실제 Cloud Tasks task ID 는 균등 분포 hash prefix 를 사용한다.
- 샤드 매핑 함수: `parseInt(adisonUidHash.slice(0, 8), 16) % 10`.
- batch manifest 는 `endRound` 함수 안에서 persisted `batches/{i}` 문서로 사전 고정하며, publish 재시도 중 재산출하지 않는다. partial manifest 충돌은 `manifestStatus = "failed"` 로 고정해 운영자 복구 대상으로 둔다.
- `endRound` 멱등 가드는 `currentRound == n` AND ((`phase == "select"` AND `now() >= roundEndsAt`) OR (`phase == "reveal"` AND (`manifestStatus != "ready"` OR `processedBatchCount < expectedBatchCount`))) 두 분기.
- `adminChoice` 는 `endRound` 첫 진입 트랜잭션 안에서만 `crypto.randomInt(0, 3)` 으로 결정하고 `revealedAt` 과 함께 set 한다. 재시도 분기에서는 재추첨하지 않는다.
- 멱등성 단위: Pub/Sub 는 `(roundNumber, batchIndex)` + player `lastProcessedRound`, Cloud Tasks 는 결정적 task name.
- 마감 검증은 항상 `Timestamp.now()` 서버 시간.
- 라운드 중 한 번만 제출 인정 (변경 허용 여부는 13장 미결정).
- `aliveCount` 보정 실행 시점은 첫 라운드 시작 직전과 각 라운드 종료 직후다. 다음 라운드 시작은 직전 종료 보정값을 사용해 중복 합산을 피한다. `totalPlayers` 는 첫 라운드 시작 직전에 한 번 고정한다. 보정 주체는 13장 미결정이다.
- 다음 라운드 예약은 `processedBatchCount` 가 `expectedBatchCount` 에 도달한 완료 finalizer 가 결정적 task name 으로 enqueue.
- `minInstances` 활성화 원칙·시점만 본 장에서 정의. 구체 값·비용은 11장.
- OIDC 검증은 Cloud Tasks → endRound 호출 시 `serviceAccountEmail` + `audience` 매칭.
- `processBatch` 는 1000명 갱신을 단일 Firestore 트랜잭션에 묶지 않는다. `batches/{i}.status`/`startedAt` lease 와 `players/{userId}.lastProcessedRound` 의 두 단계 가드로 부분 실패를 흡수한다. batch 최종 집계는 persisted UID range 재조회 기준이며, 탈락 차감은 저장된 `aliveShardIndex` 기준이다.

### 미결정 (모두 13장 위임)

| 항목 | 결정 필요 내용 |
|---|---|
| `adminChoiceHash` (commit-then-reveal) | 투명성 강화를 위해 라운드 시작 시 hash 만 저장 후 reveal 시점 공개 도입 여부 |
| `aliveCount` 보정 *주체* | 합산 호출이 페이즈 전환 함수 내부에 직접 들어가는지 별도 주기 집계 함수가 담당하는지 |
| 라운드 중 선택 변경 | 최초 제출만 인정 / 마감 전 자유 변경 중 선택 |
| TTL 트리거 주체 | Scheduled Function 주기 정리 / Firestore TTL feature `expiresAt` 필드 / Cloud Tasks 예약 정리 중 선택 |
| `minInstances` 구체 값 | 비용 시뮬레이션과 함께 11장에서 결정 |
