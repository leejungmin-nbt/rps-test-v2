## 7.2 설계 원칙

- **단일 서버 쓰기 게이트웨이 안에서 동시성 처리** — 모든 도메인 쓰기는 Cloud Functions 단일 진입점만 수행한다. 동시성은 함수 내부 트랜잭션과 분산 자료구조로 흡수한다.
- **모든 상태 전이는 트랜잭션** — 입장, 라운드 시작, 라운드 종료, 우승 확정 등 상태 전이는 트랜잭션 안에서 검사·갱신을 한 번에 처리한다. 트랜잭션 가드 없이 두 갱신을 분리하면 중복 실행과 부분 갱신이 끼어들 여지가 생긴다.
- **분산 카운터로 단일 문서 경합 회피** — 1만 명이 한 카운터 문서에 동시에 쓰는 패턴은 Firestore의 단일 문서 쓰기 한도를 넘는다. 생존자 수처럼 입장 직후 갱신되는 카운터는 10개 샤드로 분산한다.
- **중복 차단 기준 키 = `adisonUid`** — `clickKey` 는 같은 사용자라도 광고 클릭마다 새로 발급될 수 있어 중복 차단 기준으로 부적합하다. 차단 키는 URL `uid` 를 정규화·해시한 `adisonUidHash` 다.
- **입장-탈락 샤드 대칭성** — 한 사용자가 입장 시 들어간 샤드와 탈락 시 차감되는 샤드가 같아야 한다. 분포가 비대칭이면 일부 샤드 카운트가 음수가 되어 합산 결과가 왜곡된다.
- **본인 상태만 실시간 구독** — 사용자는 자기 `games/{gameId}/players/{userId}` 만 `onSnapshot` 한다. 공통 상태는 폴링한다. 이 비대칭 구독 정책은 라운드 전환 같은 공통 갱신이 1만 listener 로 즉시 fan-out 되는 비용을 평탄화한다.
- **정원 최대 +5% 초과 허용** — 근사 게이트를 선택할 경우 목표 정원 대비 최대 +5% 수준의 초과 입장을 운영적으로 허용한다. 단, 이 한계는 입장 트랜잭션이 모든 샤드를 매번 읽지 않는다는 전제 위에서만 성립한다.

## 7.3 정원 게이트

### 7.3.1 게이트의 목표와 최대 +5% 한계 근거

정원 게이트의 목표는 단일 게임 회차에 동시 참여하는 사용자 수를 운영적으로 제어하는 것이다. 본 시스템은 분산 자료구조 위에서 게이트를 운영하며, 정확한 1명 단위 cutoff 은 보장하지 않는다.

중요한 제약은 입장 트랜잭션이 **모든 샤드 문서를 매번 읽으면 분산 카운터의 효과가 사라진다**는 점이다. Firestore 트랜잭션은 읽은 문서가 외부에서 수정되면 재시도된다. 따라서 모든 입장 트랜잭션이 `alive_0~9` 전체를 read set 으로 잡으면, 어느 샤드에서든 입장이 commit 될 때 다른 트랜잭션들이 재시도될 수 있고, 대량 입장 순간에 경합·재시도·지연이 커진다.

따라서 본 장의 기본 정원 게이트는 정확 합산 게이트가 아니라 **근사 admission gate** 로 정의한다. 입장 시에는 사용자의 결정적 샤드만 갱신하고, 게이트 판단은 별도 roll-up 캐시 또는 샤드별 quota 같은 저경합 신호를 사용한다. 이 방식에서는 목표 정원 대비 최대 +5% 수준의 초과 입장을 운영적으로 허용한다. 정확도가 더 중요하면 7.3.5 의 강제 방식 옵션을 검토한다.

### 7.3.2 생존자 분산 샤드 카운터 `alive_0~9`

생존자 수는 `games/{gameId}/counters/alive_0` 부터 `games/{gameId}/counters/alive_9` 까지 10개 샤드 문서로 분산한다. 각 샤드 문서의 필드 정의와 권한은 6장 6.8.7 정본을 따른다.

샤드 매핑은 결정적으로 한다. 같은 사용자의 재호출이 같은 샤드로 가야 입장-탈락 대칭성과 멱등성 추적이 단순해진다. 본 장은 "결정적이기만 하면 된다"는 원칙만 고정하고, 매핑 함수 자체는 8장에서 한 가지로 확정한다. 참고 후보는 다음 두 가지다.

- 6장 6.6 및 6.8.6 정본의 `sha256(normalize(adisonUid))` 결과를 16진수로 본 뒤 mod 10 으로 나눈 값을 그대로 샤드 인덱스로 사용. 새 해시를 도입하지 않아도 되어 단순하다.
- 별도의 균등 분포 해시(예: 32-bit non-cryptographic hash)를 Firebase Auth UID 또는 `adisonUid` 에 적용한 뒤 mod 10. 분포 균등성을 직접 통제할 수 있다.

어느 쪽이든 `(사용자, 게임)` 조합이 정해지면 샤드 인덱스도 정해진다는 점만 유지되면 본 장의 정책은 그대로 성립한다. 구현 시에는 입장 시 결정된 샤드 인덱스를 `players/{userId}` 또는 동등한 restricted 문서에 저장해야 한다. 해시 함수 변경, 정규화 규칙 변경, 샤드 수 변경이 있더라도 탈락 차감은 **입장 당시 저장된 샤드 인덱스** 를 기준으로 해야 한다.

### 7.3.3 입장-탈락 샤드 대칭성 원칙

본 시스템은 카운터 차감을 입장 시 들어간 샤드와 같은 샤드에 적용한다. 이 원칙을 지키지 않으면 일부 샤드 카운트가 음수가 될 수 있다.

가령 입장 분포가 샤드 0~9 에 균등하게 1,000명씩 있다고 하자. 라운드 종료 시점에 탈락자 5,000명을 0~9 샤드에 균등하게 -500 씩 적용한다고 해 보자. 차감이 *실제 탈락한 사용자의 입장 샤드*와 무관하게 일어나면, 어떤 사용자는 자기 샤드를 떠나지 않았는데도 다른 샤드의 카운트가 줄어든 상태가 된다. 전체 합산은 한 라운드 동안은 맞아 보일 수 있다. 그러나 다음 라운드의 탈락 분포가 또 비대칭이면 일부 샤드 카운트가 음수가 되고, 그 시점부터 합산은 신뢰할 수 없게 된다.

따라서 차감은 항상 *탈락 사용자의 입장 시점 샤드* 를 기준으로 한다. 라운드 종료 시점의 배치 처리 안에서, 탈락자 명단을 입장 시 샤드 인덱스 별로 그룹핑한 뒤 그룹별 합계를 그 샤드에 한 번에 차감한다. 이 패턴이면 1명마다 매번 -1 호출을 보내지 않으므로 라운드 종료 시점의 쓰기 폭이 함께 줄어든다. 구체적인 구현 패턴(`Map<shardId, count>` 같은 자료구조 사용 여부, 배치 단위 호출 방식)은 8장에서 다룬다.

### 7.3.4 정원 검증 흐름

정원 검증은 입장 트랜잭션 안에서 수행하되, 입장 트랜잭션이 `alive_0~9` 전체를 매번 읽지는 않는다. 흐름은 다음과 같다.

1. URL 파라미터를 정규화한 뒤 `claims` / `players` 재호출 분기를 먼저 확인한다. 이미 입장한 본인 재호출은 정원 게이트를 다시 태우지 않는다(7.4.3).
2. 신규 입장인 경우 게임 페이즈가 `waiting` 의 입장 수락 구간에 있는지 확인한다. `countdown` 으로 전이된 뒤에는 신규 입장을 거부한다.
3. 입장 마감 시각(`closesAt`) 을 서버 timestamp 기준으로 검증한다. 클라이언트 시계는 신뢰하지 않는다.
4. 선택된 정원 강제 방식의 저경합 신호를 확인한다. 기본 근사 게이트에서는 별도 admission roll-up, 샤드별 quota, 또는 13장에서 확정한 동등한 신호를 사용한다.
5. 게이트가 통과되면 중복 차단 선점과 플레이어 생성으로 진행한다. 게이트가 닫혔으면 입장을 거부한다.

본 게이트는 첫 `countdown` 이 시작되는 순간 닫힌다. 즉, 게임이 시작된 뒤에는 정원 신호와 무관하게 신규 입장을 받지 않는다. 이 마감 경계는 페이즈 전환 트랜잭션 안에서 함께 처리된다.

### 7.3.5 정원 강제 방식 옵션

정원을 정확히 1명 단위로 끊고 싶다면 분산 샤드 카운터만으로는 부족하다. 본 장은 다음 세 옵션을 검토 대상으로 두고, 최종 선택은 13장 미결정 큐로 위임한다.

| 옵션 | 동작 | 장점 | 한계 |
|---|---|---|---|
| (a) 사전 발급 `adisonUid` 수 제한 | 매체사가 발급하는 `adisonUid` 수 자체를 정원과 같게 통제 | 게이트 자체가 외부에 위임되어 본 시스템의 동시성 부담이 줄어든다 | 매체사 통제 가능성·발급 오차에 의존한다 |
| (b) 근사 admission gate | 결정적 샤드 갱신 + 별도 roll-up 캐시 또는 샤드별 quota 로 입장 허용 여부 판단 | Firebase 단독으로 운영, 단일 hot document 회피 | 목표 정원 대비 최대 +5% 초과 입장 가능, 구현 전 게이트 신호 확정 필요 |
| (c) 대기열/큐 | 입장을 큐에 넣고 정원만큼만 통과시킴 | 정확도가 가장 높음 | 큐 인프라와 사용자 대기 UX 추가 |

옵션 선택은 (i) 1명 단위 정확도가 PM 의도상 필수인지, (ii) 매체사 발급 통제가 가능한지, (iii) 큐 인프라·UX 추가 부담을 감수할 수 있는지에 따라 결정된다. 본 장은 옵션과 트레이드오프만 명시한다.

## 7.4 중복 참여 차단

### 7.4.1 차단 키 = `adisonUid` 근거

같은 사용자가 한 게임 회차에 두 번 참여하는 것을 막는 기준 키는 URL `uid` 를 정규화·해시한 `adisonUidHash` 다. `clickKey` 는 같은 사용자라도 광고 클릭이나 진입 시점마다 새 값으로 발급될 수 있다. `clickKey` 를 차단 키로 쓰면 같은 사용자의 두 번째 클릭이 새 값으로 들어와 첫 번째 입장과 충돌하지 않으므로 중복 참여를 놓치게 된다.

`clickKey` 는 우승자 수동 지급 확인용 외부 키로만 사용한다. 이 구분은 5장 5.5 의 식별자 책임 분리와 같은 원칙을 따른다.

### 7.4.2 정규화·해시 규칙은 6장 정본을 따른다

`adisonUid` 의 정규화 규칙(유니코드 정규화, 양끝 공백 처리, 대소문자 보존 여부)과 해시 함수 선택, `claims` 문서 ID 와 동일하게 사용하는 `adisonUidHash` 의 표현 방식은 6장 6.6 및 6.8.6 정본을 따른다. 본 장은 이 규칙을 다시 정의하지 않으며, 정본 변경 시 본 장의 흐름은 그대로 유효하다.

### 7.4.3 `claims/{adisonUidHash}` 선점 흐름

중복 참여 차단은 `joinGame` Callable Function 한 곳에서만 일어난다. 클라이언트는 `claims` 문서를 직접 만들 수 없다. 함수 안에서는 다음 분기를 한 트랜잭션으로 묶는다.

1. `request.auth.uid` 로 호출 주체 Firebase Auth UID 를 확인한다.
2. URL 파라미터 5종을 서버에서 다시 정규화하고, `adisonUid` 로부터 `adisonUidHash` 를 만든다.
3. `games/{gameId}/claims/{adisonUidHash}` 와 본인 `players/{userId}` 문서를 읽는다.
4. `claims` 가 이미 존재하고 `claims.userId == request.auth.uid` 이면 본인 재호출이다. 정원·입장 마감 검증을 다시 태우지 않고 기존 player 상태를 기준으로 idempotent 정상 응답을 반환한다.
5. `claims` 가 이미 존재하고 `claims.userId != request.auth.uid` 이면 같은 `adisonUid` 의 다른 세션 재호출이다. 7.4.4 매트릭스에 따라 거부하거나, `ended` 에서는 공개 결과만 노출한다.
6. `claims` 는 없지만 본인 `players/{userId}` 가 이미 존재하면 같은 Firebase Auth UID 가 다른 `adisonUid` 로 재진입한 것이다. 한 Auth UID 가 한 회차에 여러 player 를 만들 수 없으므로 거부한다.
7. `claims` 와 본인 player 가 모두 없으면 신규 입장이다. 이때 게임 페이즈·입장 마감·정원을 검증한다(7.3.4).
8. 신규 입장이 통과되면 같은 트랜잭션 안에서 `claims` 문서를 create 하고, 본인 `players/{userId}` 문서를 create 하고, 결정적 샤드 매핑으로 정해진 `counters/alive_{shardIndex}` 의 `count` 를 +1 한다. 입장 시 결정된 `shardIndex` 는 탈락 차감용으로 함께 저장한다.

이 분기가 한 트랜잭션 안에서 처리되어야 (i) 같은 `adisonUid` 로 동시에 들어온 두 호출 중 하나만 신규 입장으로 통과하고 (ii) 본인 재호출은 정원 초과나 페이즈 전환 이후에도 복원되며 (iii) 통과한 호출에서 플레이어 문서와 카운터가 함께 갱신된다. 트랜잭션 외부에서 단계가 분리되면 "claims 는 만들었지만 player 가 빠진" 같은 부분 상태가 생길 수 있다.

### 7.4.4 재호출 정책 매트릭스

같은 사용자가 어떤 식으로든 다시 호출했을 때 어떻게 처리하는지를 게임 페이즈와 식별자 동일성 두 축으로 정리한다. 이 표는 사용자가 마주칠 모든 진입 시도를 일관된 규칙으로 처리하기 위한 기준이다.

| 게임 페이즈 | 같은 `adisonUid` + 같은 Firebase Auth UID | 같은 `adisonUid` + 다른 Firebase Auth UID | 다른 `adisonUid` + 같은 Firebase Auth UID | 신규 `adisonUid` + 신규 Firebase Auth UID |
|---|---|---|---|---|
| `waiting` (입장 수락 구간) | 본인 player 문서가 이미 존재 → idempotent 정상 응답 | `claims` 선점이 차단 → 거부 | 이미 해당 Auth UID 의 player 가 존재 → 거부 | 정원 검증 통과 시 입장 |
| `countdown` / `select` / `reveal` | 본인 화면 재로딩 허용 (생존 상태·라운드 진행은 player 문서에 보존) | `claims` 선점이 차단 → 거부 [^a] | 신규 입장 거부, 기존 player 상태 반환 또는 거부 코드 반환 | 신규 입장 거부 (입장 게이트는 이미 닫힘) |
| `ended` | 본인 결과 화면 노출 | 결과 화면 노출 (공개 정보 한정) | 결과 화면 노출 (공개 정보 한정), 기존 player private 상태는 본인에게만 노출 | 신규 입장 거부, 결과 화면만 노출 |

[^a]: 라운드 중 같은 `adisonUid` 의 재호출에 대해 기본 정책은 **거부만 수행**이다. 본인 player 문서를 즉시 `eliminated` 로 갱신하는 옵션은 URL 유출·공유·악의적 replay 로 정상 참가자를 탈락시킬 수 있는 위험이 있으므로 13장 미결정 큐에서 별도 보안 검토 후 결정한다.

본 매트릭스는 "입장·재진입 도메인 쓰기는 `joinGame` 단일 진입점" 원칙 위에서 함수 안의 분기로 구현된다. 분기 코드와 거부 응답 코드 표는 8장에서 다룬다.

## 7.5 페이즈 전환 동시성 가드

페이즈 전환은 입장과 함께 동시성이 가장 민감한 구간이다. 트랜잭션 가드 없이 두 갱신을 분리하면 중복 실행과 부분 갱신이 끼어든다. 본 장은 가드의 원칙 4개만 요약하고, 페이즈별 트랜잭션 상세 표는 8장에서 다룬다.

- 모든 페이즈 전이는 트랜잭션 안에서 현재 페이즈와 라운드 번호의 일치를 검사한 뒤 갱신한다. 이미 다음 페이즈로 넘어간 게임에 대한 늦은 전이 호출은 무시된다.
- `games.phase`, `games.currentRound`, `games.roundEndsAt` 는 같은 트랜잭션 안에서 함께 갱신한다. 클라이언트가 새 페이즈는 봤지만 새 라운드 번호는 아직 못 본 엇갈린 스냅샷을 읽지 않게 한다.
- 라운드 종료 트리거(`endRound`)는 결정적 task name 또는 트랜잭션 가드 안에서 한 번만 실제 처리되도록 멱등 처리한다. Cloud Tasks 의 재시도, 클라이언트 트리거의 중복 호출 모두 같은 멱등 가드를 거친다.
- 1만 명 일괄 판정은 `processBatch` 가 1000명 단위 배치로 분산 처리한다. `games/{gameId}/rounds/{n}/batches/{i}.status` 문서는 같은 batch dispatch 의 중복 실행을 막는 1차 가드다. 다만 player 업데이트, 샤드 차감, batch status 갱신이 하나의 원자적 단위로 묶이지 않는 구현에서는 `players.lastProcessedRound` 같은 player-level 가드도 함께 사용한다. 즉 batch status 는 dispatch 멱등성, player-level guard 는 side effect 멱등성을 담당한다.

## 7.6 `aliveCount` 공개 캐시 보정

공개 화면이 사용하는 `games.aliveCount` 는 표시용 캐시다. 입장마다 이 단일 문서를 직접 +1 하면 단일 문서 쓰기 한도에 부딪힌다. 따라서 입장 트랜잭션은 분산 샤드 카운터(7.3.2)만 갱신하고, 공개 캐시는 별도 시점에 보정한다.

- **입장 시** — 분산 샤드 카운터 1개만 +1 한다. `games.aliveCount` 는 갱신하지 않는다.
- **첫 라운드 시작 직전** — 10개 샤드를 합산해 `games.aliveCount` 를 보정하고, `games.totalPlayers` 를 최종 참가자 수로 한 번 고정한다. 이후 `totalPlayers` 는 누적 참가자 수 의미를 유지하므로 생존자 감소에 따라 줄이지 않는다.
- **라운드 종료 직후** — 배치 처리에서 탈락자별 차감을 입장 시 샤드 기준으로 적용한 뒤(7.3.3), 다시 10개 샤드를 합산해 `games.aliveCount` 를 보정한다. `games.totalPlayers` 는 변경하지 않는다.

이 보정은 사용자에게 보이는 생존자 수 숫자가 라운드 경계에서 정확히 갱신되도록 한다. 라운드 도중에는 본 캐시가 잠시 stale 일 수 있으나, 사용자 관점에서는 라운드 결과가 공개되는 시점에 새 숫자로 갱신되어 보이면 충분하다.

보정 트리거 주체(주기적 집계 함수 vs `startRound` / `endRound` 내부 합산)는 13장 미결정 큐로 둔다.

## 7.7 새로고침 / 이탈 시나리오

본 시스템은 사용자의 세션 이탈을 실시간으로 감지하지 않는다. Firestore 는 presence 시스템이 아니다. 클라이언트가 페이지를 닫거나 네트워크가 끊어졌다는 신호는 서버에 즉시 도달하지 않으며, 도달하더라도 본 시스템은 그 신호를 도메인 처리에 사용하지 않는다.

이탈의 효과는 두 가지 메커니즘의 조합으로 발현된다.

- **재진입 시도 시 정책 적용** — 사용자가 다시 진입하면 7.4.4 매트릭스의 분기를 따른다. 같은 `adisonUid` + 같은 Firebase Auth UID 조합이면 본인 화면이 복원되고, 다른 Firebase Auth UID 면 `claims` 선점이 차단한다.
- **미제출 시 라운드 종료 탈락** — 페이지를 떠난 사용자가 `select` 마감까지 선택을 제출하지 않으면 3장의 미제출자 정책에 의해 해당 라운드에서 탈락한다.

세부 시나리오는 다음과 같다.

- **같은 기기에서 새로고침** — Firebase Anonymous Auth UID 가 유지된다. 본인 `players/{userId}` 문서를 다시 `onSnapshot` 으로 구독하면 현재 페이즈·생존 상태·선택 라운드가 즉시 복원된다. 사용자는 화면이 복원된 시점부터 정상적으로 게임을 이어간다.
- **시크릿 모드 또는 다른 기기 재진입** — Firebase Anonymous Auth 가 새 UID 를 발급한다. URL `uid` 즉 `adisonUid` 는 동일하므로 `claims/{adisonUidHash}` 선점이 막아 신규 입장을 거부한다. 결과적으로 같은 사용자가 다른 세션으로 갈아타며 두 번 참여하는 것을 차단한다.
- **페이지를 그대로 떠남** — 본인 player 문서는 보존된다. 라운드 마감 전에 돌아오면 본인 화면이 복원되지만, 마감까지 선택을 제출하지 않으면 미제출자 정책으로 탈락한다. "라운드 중 페이지 이탈만으로도 즉시 자동 탈락 처리할지" 같은 강도 조정은 13장 미결정 큐로 둔다.

"참여자가 게임 중 페이지를 유지해야 한다"는 사용자 안내 문구·UX 디자인은 본 장이 아니라 작성 예정 10장에서 다룬다.

## 7.8 확정 사항과 미결정 사항

### 확정

- 중복 차단 기준 키는 `adisonUid` 다. `clickKey` 는 차단 키로 사용하지 않는다.
- 중복 차단은 `joinGame` 단일 진입점 안의 트랜잭션에서 `claims/{adisonUidHash}` 선점으로 수행한다. 클라이언트 직접 create 는 차단한다.
- 생존자 카운터는 10개 샤드(`alive_0` ~ `alive_9`)로 분산하며 결정적 샤드 매핑을 사용한다.
- 입장-탈락 샤드 대칭성 원칙을 지킨다. 차감은 탈락 사용자의 입장 시 저장된 샤드 기준으로 그룹핑해 적용한다.
- 근사 정원 게이트를 선택할 경우 목표 정원 대비 최대 +5% 초과 가능성을 운영적으로 허용한다. 정원은 보수적으로 설정한다.
- 본인 `players/{userId}` 만 실시간 구독한다. 공통 상태는 폴링한다.
- 모든 페이즈 전이는 트랜잭션 가드 안에서 처리하며, `endRound` 와 배치 처리는 멱등성 단위를 가진다.
- `games.aliveCount` 공개 캐시는 입장마다 갱신하지 않고 라운드 경계에서 샤드 합산으로 보정한다.
- Firestore 는 presence 시스템이 아니다. 이탈 효과는 재진입 시 정책 + 미제출 탈락의 조합으로 발현된다.

### 미결정 (모두 13장 위임)

| 항목 | 결정 필요 내용 |
|---|---|
| 운영 정원 N | 5천/1만/1.5만 등 구체값 |
| 정원 강제 방식 | (a) 사전 발급 `adisonUid` 수 제한 / (b) 근사 admission gate 의 roll-up 또는 샤드별 quota / (c) 대기열·큐 중 선택 |
| 라운드 중 같은 `adisonUid` 재호출 자동 탈락 강도 | 기본은 거부만 수행. 즉시 `eliminated` 갱신 옵션은 replay 악용 가능성까지 검토해 선택 |
| 페이지 이탈 시 자동 탈락 강도 | 미제출 정책에 위임할지, 별도 감지 메커니즘을 도입할지 |
| `aliveCount` 캐시 보정 트리거 주체 | 주기적 집계 함수 vs 페이즈 전환 함수 내부 합산 |
| `claims` / `players` / `counters` TTL 보존 기간 | 종료 후 며칠까지 보관하고 어떤 순서로 정리할지 |
