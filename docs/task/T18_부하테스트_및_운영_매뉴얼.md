# T18 — 부하 테스트 + 인앱웹뷰 QA + 운영 매뉴얼

> 운영 전 마지막 검증 단계. 1만 동접 부하 테스트, NBT 오퍼월 인앱웹뷰 QA, 운영자 매뉴얼 (10장 확장) 을 수행한다.

## 가이드 정본

- [10. 운영 정책 및 관리자 업무](../guide/10_운영_정책_및_관리자_업무.md) 전체 (스텁 → 확장)
- [12. 부하테스트 및 검증 계획](../guide/12_부하테스트_및_검증계획.md) 전체 (스텁 → 확장)

## 선행

- 페이즈 1 ~ 4 모두

## 구현 항목

### 부하 테스트 도구 / 시나리오

- [ ] 도구 채택 (k6 또는 Artillery)
- [ ] 단계 부하: 1k → 5k → 1만 (12.2)
- [ ] 시나리오 매트릭스
  - 입장 처리: 정원 게이트, 중복 참여, `claims` 선점 경합
  - 라운드 처리: 선택 제출, 미제출 탈락, 라운드 전환 지연
  - batch 처리: Pub/Sub fan-out, batch 실패/재시도, 집계 정합성
  - 비용 측정: Firestore/Functions/Tasks 사용량 ↔ 11장 가정 비교

### 인앱웹뷰 호환성 QA

- [ ] NBT 오퍼월 webview 진입 검증 (실 단말 또는 시뮬레이션)
- [ ] 5종 쿼리 파라미터 유지 검증 (URL 보존, redirect 시 손실 없음)
- [ ] `index.html` 캐시 동작 검증 (인앱웹뷰 stale 번들 미발생)
- [ ] iOS / Android 주요 단말 매트릭스

### 운영 매뉴얼 확장 (10장)

- [ ] 행사 시작/종료 절차
  - `appState/activeGameId` 갱신
  - 이전 `games/{gameId}` 회차 정리 (수동 / 자동 어느 쪽 채택할지)
  - 시작 전 체크리스트
- [ ] `minInstances` 운영
  - 활성화 시점 (행사 시작 30분 전, 8.11)
  - 비활성화 시점 (행사 종료 직후)
  - 담당자 / 권한
- [ ] 우승자 확인 / 수동 지급
  - `result/summary` 와 `winnerPrivate/summary` 확인 절차
  - 지급 책임자 / 감사 기록 방식
  - `delivered`, `deliveredAt`, `deliveryMemo` 갱신 주체
- [ ] 장애 대응
  - `batches/{i}.status == "failed"` 복구 절차
  - `manifestStatus == "failed"` 복구 절차
  - 라운드 멈춤 시 진단 단계 (큐 → 함수 로그 → batch 상태)
- [ ] 알림 / 보고
  - 알림 채널 구체값
  - 사고 보고 라인
  - 비밀 회전 절차 (9.8 사고 시)
- [ ] 감사 / 보존
  - 지급 처리 기록 보관
  - 개인정보 보존·삭제 정책 (13장 결정 반영)

### 운영 리허설

- [ ] dev 환경에서 1k 부하 + 1라운드 끝까지 진행 1회
- [ ] prd 환경에서 운영자 매뉴얼 따라 dry-run 1회 (실제 트래픽 0)

## 완료 조건

- [ ] 1만 동접 시나리오에서 라운드 누락 0건, 모든 batch `done`
- [ ] `aliveCount` 가 모든 라운드 경계에서 샤드 합산과 ±0 일치
- [ ] 정원 ±5% 한계 내에서 입장 cutoff 동작
- [ ] 인앱웹뷰 단말 매트릭스에서 진입 → 우승까지 e2e 완주
- [ ] 운영자 매뉴얼이 10장에 정본화되어 PM 리뷰 통과
- [ ] dry-run 운영 리허설 회고록이 작성되어 잔여 항목이 13장에 반영됨

## 위임 / 미결정

- 운영 정원 N → 13장 (테스트 결과로 권고값 제안)
- 정원 강제 방식 (a/b/c) → 13장 (테스트 결과로 트레이드오프 정량화)
- 라운드 수 / 라운드 시간 → 13장
- 제세공과금 22%, 이월 누적 정책 → 13장
